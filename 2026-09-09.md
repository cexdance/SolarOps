### What happened

Cesar messaged Andrea Alvarez in the Messages screen and asked why she got no
notification. She did receive the message (read at 23:12:49, replied 23:13:29),
but nothing appeared in her bell.

Root cause: **DMs never created a notification of any kind.**
`lib/messenger.ts sendMessage` wrote the `messages` row and called nothing else.
The `notifications` table had only two types in 1,085 rows: `mention` (833) and
`new_lead` (252). There was no `message` type at all. Working as written, not a
regression.

### Change

- `lib/messenger.ts`: `sendMessage` fires `POST /api/notify` with `kind:'dm'`
  after the row stores. Fire-and-forget, so a notify failure cannot fail a send.
- `api/notify.ts`: the existing mention path takes an `isDm` branch. Same JWT
  verify, same targeted admin lookup, same insert, same web push. Different
  title/type, and **email is skipped for DMs**.
- `types/index.ts`: `'message'` added to `AppNotification['type']`.
- `components/Layout.tsx`: a Messages chip in the bell's filter row, and a
  click on a `message` notification opens the Messages screen (a DM carries no
  job or customer id, so the existing routing would have been a dead click).
- `__tests__/dmNotification.test.ts`: 2 tests. 749 pass total, build green.

### Patterns worth reusing

- **RULE: a client cannot notify another user directly here.**
  `public.notifications` has SELECT and UPDATE policies only, both
  `auth.uid() = user_id`. There is no INSERT policy, so every cross-user
  notification must go through `/api/notify` under the service role. Any future
  "tell user X" feature inherits this constraint.
- **RULE: an in-app feature that stores a row is not a delivered feature.**
  The messenger worked perfectly and still felt broken, because delivery is the
  bell plus push, and neither was wired.
- **RULE: skip email on high-frequency events.** One Resend email per chat
  message would get `notifications@conexsol.us` filtered wholesale, taking the
  mention emails down with it.

## ce86b6e: nightly end-of-day workload report (and a 4-minute outage I caused)

Deployed and verified: `version.json` sha `ce86b6e`, `/api/notify` back to 405,
`/api/notify?action=daily-report` returns 503 `CRON_SECRET not configured`,
`/api/users` 401. 808 tests pass.

### What shipped

A Vercel cron calls `/api/notify?action=daily-report` at 03:00 UTC (23:00
Eastern) and emails that day's Team Workload summary to an admin-managed
recipient list, with an optional Telegram leg.

- `api/_dailyReport.ts` - window, fetch, render, delivery, orchestration.
- `api/_activityStats.ts`, `api/_dailyReportConfig.ts` - deliberate copies.
- `api/notify.ts` - cron branch, lazily importing the report module.
- `vercel.json` - `crons` entry (3-line diff).
- `solarflow-dashboard/src/lib/dailyReportConfig.ts` + `DailyReportSettings.tsx`
  - Settings UI, gated on `users.manage`.
- `syncEngine.ts` - `solarops_daily_report` added to `KV_SYNC_KEYS`.

### ⚠ THE OUTAGE: api/ MUST NOT IMPORT FROM THE APP SOURCE

The first version (`ad5c9b9`) imported the session math from
`../solarflow-dashboard/src/lib/activityStats`. Result: **every branch of
`/api/notify` returned `FUNCTION_INVOCATION_FAILED`**, taking @mentions,
contractor-paid notifications, site-transfer and appointment mail down with
it. Reverted in `2c820f1`; the endpoint was 500 for roughly four minutes.

**RULE: a green build proves NOTHING about a serverless function.** The Vercel
build logs were clean. `esbuild --bundle` of the same file loaded fine in local
Node. It still failed at runtime in the deployed lambda. `trello-card.ts`
already documents this boundary (it duplicates `labelCatalog` rather than
importing it); I crossed it anyway.

**RULE: never import an optional feature at module scope in a shared endpoint.**
This is the third time this exact shape has bitten this file. The VAPID guard
directly above my branch exists for the same reason and says so in a comment.
`_dailyReport` is now imported with `await import()` INSIDE the cron branch, so
the worst case is a broken nightly report rather than a broken notification
endpoint.

**RULE: the pre-deploy gate for an api/ change is to load the bundled function
in Node and exercise every branch**, not `npm run build`:
`esbuild api/notify.ts --bundle --platform=node --format=cjs` then require it
and call the handler. That reproduces import-time crashes in seconds. It now
verifies POST 401, GET 405, cron 503/401/500.

Copies are pinned to their originals by `dailyReportParity.test.ts` (fixtures
through `buildWorkload`, `normalizeConfig`, thresholds, bot list) so the email
and the Ops Center widget cannot drift into different hours for the same day.

### ⚠ PRODUCTION HAS NO RESEND_API_KEY, SO ALL APP EMAIL IS INERT

`vercel env ls` shows only 8 variables across every environment:
`SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_URL`, `TRELLO_API_KEY`,
`TRELLO_API_TOKEN`, `VITE_CLIENT_REGISTRY_URL`, `VITE_SUPABASE_ANON_KEY`,
`VITE_SUPABASE_URL`, plus a Development copy of the registry URL.

Missing: **`RESEND_API_KEY`**, `VAPID_*`, `CRON_SECRET`, `TELEGRAM_BOT_TOKEN`,
`SOLAREDGE_API_KEY`, `XERO_CLIENT_SECRET`.

So every Resend path (`notify.ts` site-transfer, customer-appointment,
contractor-paid, @mention mail, `send-quote.ts`, and this report) is silently
returning `skipped: 'no RESEND_API_KEY'` in production **right now**. It fails
open with a 200, which is why nobody noticed. This also explains the long
"web push unproven" note: there are no VAPID keys either.

The local `.env.vercel.prod` DOES contain a `RESEND_API_KEY`, but that file
also carries the stale service key that 401s, so its values are not trusted
and were deliberately not copied into production.

### Still required before a single report sends

1. `vercel env add CRON_SECRET production` - without it the branch 503s by
   design rather than running unauthenticated.
2. `vercel env add RESEND_API_KEY production` - without it the run reports
   `RESEND_API_KEY not set` per delivery.
3. `vercel env add TELEGRAM_BOT_TOKEN production` - optional; Telegram stays
   inert without it and never blocks the email.
4. Redeploy after adding, so the functions pick the values up.

No env var was set by me: adding production secrets is the owner's call, and
one candidate value on disk is already known-stale.
