## 1439be6: costs covered pays the contractor, notifies them, moves their card

Live `v1.7.6.1+1439be6.1787300805257`, builtAt 2026-08-21T08:26:45Z.
Verified in the shipped bundles (Paid column, notification bell, the synced
notifications key) AND by hitting the function: `POST /api/notify` returns
**401 Unauthorized**, not a Vercel NOT_FOUND page, so the serverless function
actually built and routes.

### Ask
"When the card is marked Covered contractor and expenses, the contractor gets a
notification and the card is moved in their kanban to a paid column."
Channel choice confirmed with the user: **both email and in-app**, and **no
dollar amount**.

### The card move needed no new plumbing, only a corrected projection
The portal does NOT read the ContractorJob blob for status. It renders admin
Jobs through `pickupJobsForContractor` + `toContractorJobView`. Since
`moveToColumn('costs_covered')` already stamps `costsCoveredAt` on the admin
Job, and that syncs, the whole feature is a projection change plus a column.

`CONTRACTOR_VISIBLE_STATUSES` excluded invoiced/paid, so a card **vanished**
after completion and could never arrive in a Paid column. The billing tail is
now visible and `toContractorJobView` decides what it is CALLED.

**RULE: `woStatus: 'paid'` means the CLIENT paid, NOT the contractor.** Costs
are covered later, at `costsCoveredAt`. Mirroring the stage straight through
would have told a contractor they were paid while they were still owed.
Contractor `paid` keys off `costsCoveredAt` alone; the client-invoicing tail
reads as `completed`.

### Two guards, both found by checking live data before shipping
- **One ARCHIVED job carries `woStatus: 'paid'`.** The visibility test reads
  `woStatus ?? status`, so widening the set would have RESURRECTED it into the
  portal as Paid. `pickupJobsForContractor` now excludes archived explicitly.
- **2 contractor rows already hold a stale `status: 'paid'`** whose admin job
  was never costs-covered. The "furthest along wins" rule would have honoured
  them. That rule now applies only to FIELD progress (assigned -> completed),
  which is what it was written for, never to billing states.

### The in-app notification store was dead code
Nothing wrote it, nothing read it, and it was **not in `KV_SYNC_KEYS`**, so an
office-written notice could never leave the desktop that wrote it. Now:
- registered in `KV_SYNC_KEYS` + `KV_MERGERS` (the pairing `kvMergers.test.ts`
  enforces). Office writes, contractor marks read = multi-writer.
- `mergeContractorNotifications`: union by id, **`read` sticky-true** so marking
  read on the phone is not undone by a desktop copy, capped at 300 newest-first.
- `saveNotifications` now writes cloud-first (`dbSet` -> `setKVMirror` ->
  localStorage), same order as `saveContractorJobs`, so a quota throw cannot
  skip the durable copy.

**BUG FIXED: `addNotification` was destructive.** The comment said "keep last
100 per contractor"; the code filtered OUT every existing notice for that
contractor before prepending, so each contractor could only ever hold ONE.

New bell + inline list in the contractor header (that portal renders with no
Layout, so it needed its own).

### Email
New `contractor-paid` action on the EXISTING `/api/notify` function, a branch
not a new file (Hobby caps `api/` at 12 functions). Green header, no amount:
SHOW_MONEY hides commercial figures and their submitted invoice is the
authority on the sum.

### Firing
One choke point, `moveToColumn`, guarded on `!job.costsCoveredAt` so dragging a
card out of Costs Covered and back cannot re-send a payment confirmation.
In-app write is attempted independently of the email, so a mail outage cannot
lose the durable record.

## 9c9fb5e: paid date + green card on the contractor side

Live `v1.7.6.1+9c9fb5e.1787301863921`, builtAt 2026-08-21T08:44:23Z. Verified
in the shipped bundle: green shell classes, the solid PAID badge, the "Paid "
line and the `costsCoveredAt` projection are all present.

### Ask
"Add to the contractor the Paid date to the service card once it is marked paid
by the admin. Add a green hue to the card for quick identification."

### What changed
- **`paidAt` on `ContractorJob`**, projected from the admin Job's
  `costsCoveredAt`. Same authority rule as the status: the admin `paid` stage
  means the CLIENT paid and lands earlier, so an order nobody has covered
  carries NO date at all. The card keys its whole green treatment off that, so
  an unpaid order cannot accidentally go green.
- **List card** (`ContractorDashboard.ListCard`): green wash + green border when
  paid, a solid green PAID badge, and a `Paid Aug 18, 2026` line under the
  schedule row.
- **Detail card** (`ServiceOrderCard`, inside `JobDetail`): matching green shell
  and header plus a full-width paid banner, so opening the order tells the same
  story as the list.

### Small bug swept up
Both surfaces previously rendered `paid` in the SAME emerald as `completed`
(`ServiceOrderCard.STATUS_STYLE`), and the list card had no `paid` case at all
so it fell through to the grey default. A paid order was visually
indistinguishable from a finished-but-unpaid one, which is the exact thing this
change exists to fix.

Build green, 558/558 tests (2 new: the date is carried through, and stays
undefined until costs are covered).
