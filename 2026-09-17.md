
## 1026835: a previous visit's completion no longer re-completes a follow-up

**Report:** SO-2609-78916 had an approved second visit (quote created 09-16 18:02) but sat in Completed instead of the schedule side.

**Cause (change_log):** Cesar moved it to Scheduled 09-16 18:22. At 18:40 Daniel's browser ran `contractor-reconcile` with `advanced: true` and set it back to `completed`, restoring `completedAt` 2026-09-11 (visit 1). The contractor copy still carried visit 1's completion, and reconcile read any `completedAt` as "done".

**Fix:** `contractorLiveStatus(cj, adminJob)` in `src/lib/visits.ts`. With a follow-up open, only a `completedAt` (or `startedAt` for in progress) later than `currentVisit.requestedAt` counts. Single-visit orders unchanged. Used in the App.tsx reconcile loop.

**Files:** `solarflow-dashboard/src/App.tsx`, `src/lib/visits.ts`, `src/__tests__/contractorLiveStatus.test.ts`. 1010 tests, build OK. Live sha verified, `/api/users` 401 JSON.

**Record state:** no repair written. By 09-17 13:08Z the order had already moved to `in_progress` (visit 2 underway). It still carries the stale visit-1 `completedAt` 2026-09-11, restored by the bad reconcile; clear it if it confuses billing aging.

**Rule:** after a follow-up is requested, every per-visit stamp on a synced contractor copy is from the old visit until proven newer. Compare against `currentVisit.requestedAt`.

## 4e16c94: poisoned sync rows no longer skipped forever (SO-2606-21481)

**Symptom:** SO-2606-21481 closed repeatedly (09-09, 09-16, 09-17 x2) but kept showing in Approved.

**Evidence:** `change_log` has 18 `job.update` entries since 08-26 (dispatch, in_progress, completed, invoiced), yet `app_data job:job-1781045621481` is unchanged since 2026-08-17. Every lost write came from ONE device, `dev-1776283250266-0cj3by8` (cesar.jurado, Chrome). Same device also lost writes on SO-2609-35193 (4), WO-2605-22249 (1), WO-2605-89308 (2). No RLS/trigger/constraint can reject them; other rows from that device land.

**Cause:** `pushToSupabase` skips a row after 3 failed pushes (`solarops_poisoned_rows_v1` in localStorage). The only exit was a successful push, which a skipped row never makes. `getPoisonedKeys`/`resetAllPoison` were never called in prod. Skip was console-only.

**Fix:** `isRowPoisoned` now expires 10 min after `lastFailedAt` (legacy entries fall back to `since`, so the existing Aug 26 entries release on the next push). A skipped row throws, so the outbox stays pending and the sync error banner shows.

**Files:** `src/lib/outbox.ts`, `src/lib/syncEngine.ts`, `src/__tests__/outbox.test.ts`. 1012 tests, build OK. Live sha 4e16c94 verified, string present in bundle, `/api/users` 401 JSON.

**Pending:** no data repair written. The 4 affected orders hold their Aug/Sep-15 server state; Cesar's browser should push its local copies once it loads the new build, if the original failure does not recur. Re-check `app_data.updated_at` for those 4 keys. The original 3 failures' error is unknown (it lives only in that browser's localStorage `lastError`).

**Rule:** a retry skip-list needs an expiry; an exit condition that requires the skipped action to run is not an exit.
