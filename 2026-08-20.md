## 5efe186 — contractor mobile portal never surfaced "update available"

**Commit:** `5efe186`
**Files:** `solarflow-dashboard/src/App.tsx` (+3), `solarflow-dashboard/src/components/contractor/ContractorDashboard.tsx` (+37/-6)

### Report
"It is on the completion screen of the contractor on mobile" — Cesar closed several calls as a contractor and kept seeing the old completion splash (pre-39a4c8b/681ad04 design), despite those being deployed and live for days.

### Diagnosis
First ruled out a bad deploy: dispatched `karen` to test live with a fresh (cache-cleared) session. `version.json` sha matched `HEAD` exactly, and a real completed job (US-15665) rendered every piece of the new splash correctly (status-colored hero, client number above name, no payment card, notes/photos/expenses cards, `#FF7200` XP card). So the deployed code was never wrong — this ruled out "redeploy" as the fix before I went looking for a real cause.

Traced the actual mechanism in `useVersionPoll()` ([useVersionPoll.ts](../solarflow-dashboard/src/hooks/useVersionPoll.ts)):
- Initial mount: if stale, reloads immediately.
- Resume after 30min+ backgrounded with no pending push: reloads immediately.
- A mid-session 10-minute interval poll: only flips a `versionState` flag to `'update-available'`. Never force-reloads (correctly — no `beforeunload`/dirty-form guard exists anywhere, so an unannounced reload would eat unsaved work).

That flag is rendered as a small "Update available, click to restart" banner in `Layout.tsx:655`. But the real contractor portal (`App.tsx` `isContractorMode` branch, ~line 3095) renders `<ContractorDashboard>` **directly, with no `Layout` wrapper**. `versionState` was computed unconditionally at the top of `App.tsx` (line 950) and simply discarded for contractors. A contractor working back-to-back calls all day, phone never backgrounded 30 continuous minutes, had zero signal a new build existed and no way to trigger it short of a full force-quit.

Found a second, compounding issue while in there: the contractor header's own refresh button was titled "Sync & update to the latest version" but its handler (`handleSync`) only calls `onSync?.()`, a data pull — it never reloads the JS bundle. A contractor tapping it, believing it already fixed this, would not be wrong to think so.

### Fix
Threaded `versionState` / `remoteVersion` / `onUpdate={() => window.location.reload()}` into `ContractorDashboard`'s props (only the standalone contractor-portal render site needs it — the `case 'my-jobs':` admin-linked-contractor view at `App.tsx:3544` already sits inside `Layout`, which already had this). Header now shows the same orange "Update available" pill Layout already uses for staff, tap-to-reload, when `versionState === 'update-available'`. Corrected the Sync button's tooltip to "Sync latest job data" so it stops promising something it doesn't do.

Did not touch `useVersionPoll.ts` itself — its reload/no-reload gating is deliberately conservative (documented safety margin against destroying unsaved input) and out of scope; this fix is purely "surface the signal that already exists," not a new reload policy.

### Verification
`pnpm build` and `pnpm test` (532 tests, 56 files) both green. Live `version.json` polled and confirmed `sha: "5efe186"`, builtAt `2026-08-20T12:47:17.664Z`. Did not get a live click-through of the new banner itself (can't force a stale-build state against a fresh live deploy to trigger `'update-available'` on demand); confidence rests on this being a straight prop-thread of an already-shipped, working pattern (Layout.tsx's identical banner) plus a clean build/typecheck.

### Follow-up
None identified. If this recurs, the next thing to check is whether the 10-minute poll interval itself is too long for a contractor's actual call cadence, but there's no evidence yet that it is — this fix addresses "the signal was never shown," not "the signal is too slow."

## e50ccef — the screenshot that revealed a second, unrelated bug

Restyled to the splash's solid `#FF7200` card language (white/20 dividers, no separate dark/gradient page) instead of carrying over the old modal's own visual system.

Net effect: completing a call now goes straight to one screen, colored hero, client number, XP card (with the full breakdown inline when relevant), photos/files, expenses, notes. No intermediate tap.

## 6ba47b7 — SolarEdge alerts map view + session-expired false positive

**Commit:** `6ba47b7`
**Files:** `solarflow-dashboard/src/components/views/SolarEdgeAlertsMapView.tsx` (new, +192), `solarflow-dashboard/src/components/SolarEdgeMonitoring.tsx` (+45/-1), `solarflow-dashboard/src/lib/syncEngine.ts` (+9/-2)

### Report
Two asks in one thread: (1) "create a map view on the solaredge section to view the open alerts", (2) after testing, Cesar's live screenshot showed a red "Session expired, your changes are saved locally but not synced. Please re-login" toast on the SolarEdge Monitoring screen — "fix session issue and Deploy".

### Map view
Reused the existing Leaflet + Nominatim geocoding infra rather than adding a mapping dependency: same `solarops_geocode_cache` localStorage key that [JobMapView.tsx](../solarflow-dashboard/src/components/views/JobMapView.tsx) and [SiteMapView.tsx](../solarflow-dashboard/src/components/views/SiteMapView.tsx) already write to, so addresses geocoded by either of those resolve instantly here too. New `SolarEdgeAlertsMapView` takes the already-filtered site list narrowed to `alerts > 0`, geocodes each address, plots a pin colored by `highestImpact` (same palette as the table's `IMPACT_COLORS` badge), with a popup offering Open (site panel) / Acknowledge / View in SolarEdge — wired to the same handlers the table's `AlertCell` already used. Added a Table/Alerts Map toggle to `SolarEdgeMonitoring.tsx`'s filter bar; map mode renders instead of the table, table's existing filters (search/status/group/WO/client-status) still apply, alert-only narrowing is additional and specific to the map.

Verified live in-browser (staff login, SolarEdge Monitoring → Alerts Map): pins render over Florida colored by severity, click-through to a real site (US-15219) opens the slide-over panel correctly. Nominatim CORS/rate-limit failures on some addresses are pre-existing behavior of the shared `geocodeAddress` helper (same as the other two map views already in prod), not introduced here — degrades to an "X not located" indicator instead of breaking.

### Session-expired diagnosis
Tried to reproduce with a clean sign-out/sign-in cycle first: did not reproduce. Console showed the real mechanism working as designed (`[SyncEngine] push blocked: no successful pull yet this session`, stale-write guard dropping records correctly). This ruled out "broken every time" before looking for a narrower cause.

The actual trigger: this dev browser profile is shared across multiple concurrent sessions (my testing tabs and Cesar's live session, same `localhost:5173` origin, same `solarflow_auth` localStorage key). Supabase rotates the refresh token on every use — once tab A refreshes, tab B's in-flight refresh call is holding a now-stale token and gets rejected, even though a perfectly valid session (the one tab A just wrote) exists in the same storage a moment later. `getActiveSession()` in [syncEngine.ts](../solarflow-dashboard/src/lib/syncEngine.ts) declared the session dead the instant its own `refreshSession()` call failed, without ever looking at what another tab may have just written.

### Fix
Added one more `getSession()` check after a 500ms wait, only on the path where both the initial `getSession()` and `refreshSession()` came back empty. Picks up a session another tab wrote in the interim instead of surfacing the false "please re-login" banner. Did not touch the outbox/push/merge logic around it — narrow, single-function change to the exact chokepoint already responsible for this message.

### Verification
`pnpm build` (tsc -b + vite build) and `pnpm test` (532 tests, 56 files) both green. Pushed, polled `version.json` until `sha: "6ba47b7"` matched (`builtAt: 2026-08-20T15:56:40.724Z`), spot-checked `/api/users` returned `401 Unauthorized` (not a Vercel `NOT_FOUND`), confirming serverless functions actually built. Did not get a live multi-tab repro of the fixed race post-deploy (inherently timing-dependent, hard to force on demand); confidence rests on the diagnosis matching the exact observed symptom and the change being additive-only (a second read, never removes the existing refresh attempt).

### Follow-up
None identified. If the session-expired toast recurs on a *single* tab/device (not multi-tab), this fix would not address it and the real-expiry case documented in the existing comment above `getActiveSession()` should be re-examined.
