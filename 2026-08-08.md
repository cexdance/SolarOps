## 378cc7b (+ a6b1f7d): Billing intake column, CREATE QUOTE + service-orders-only

Live `v1.7.6.0+378cc7b.1786213122869`, builtAt 2026-08-08T18:18:42Z.
Bundle-verified on `assets/Billing-KEb57NHN.js` (CREATE QUOTE, the subtitle,
"Log Expense", "Review PowerCare", "Not linked to a client record" all present),
not just a version.json sha match.

### What the user asked for
1. Rename the first Billing kanban column New -> CREATE QUOTE.
2. Every newly created service order must show up there, whichever of the three
   intake flows it came from: quote, service account expense, PowerCare.
3. Then: "only customers that have a service order created will need a quote."

### a6b1f7d, the bug behind "new orders don't show up here"
Nothing was routing wrong. All three flows already start at `draft` or with no
`woStatus`, and `getBillingColumn` catches both. **They were being dropped at
render.**

`filteredJobs`'s search predicate ran even with an EMPTY query:
```js
customer?.name.toLowerCase().includes(q) || customer?.address...includes(q)
```
With no customer match that is `undefined || undefined` -> falsy -> the job
disappears from the entire board. The intake column was rendering **1 card out
of 35**. Invoiced and Ready to Invoice were each hiding one too.

Fixes: empty query short-circuits to `true`; a real query also matches
`clientName` and `siteAddress`; `displayName(job, customer)` falls back to
`clientName` then "Unnamed order"; unlinked cards show an amber "Not linked to
a client record".

**RULE: an optional-chained predicate is a FILTER THAT DELETES DATA.**
`a?.x.includes(q)` returns undefined, not false, and every row whose `a` is
missing silently leaves the view. Guard the empty case first.

### 378cc7b, and why a6b1f7d was only half right
Surfacing those 34 cards was wrong in substance: 33 of them are not service
orders. They are S1 pipeline leads, `customerId:''`, no `woNumber`, and every
single one carrying a `pipelineStage` (the field whose own type comment says
"Nothing in billing or contractor visibility reads this field").

`isServiceOrder(job) = !!job.woNumber`, applied once to a `serviceOrders` list
so kanban, list, calendar, report modal and the All/Unbilled/Invoiced/Paid
counters cannot drift apart.

**Discriminator was validated against live data BEFORE it was used:**

| | woNumber | no woNumber | no woNumber, not a lead |
|---|---|---|---|
| six worked columns | 116 | 0 | 0 |
| intake column | 2 | 33 | **0** |

Zero false positives in either direction. Chose the order number and NOT the
customer link on purpose: 2 live orders have a woNumber but no customer row and
are real work. That is also why the empty-search guard has to stay.

Result: columns 34/12/17/13/34/26/3 -> **1**/12/17/13/34/26/3, a delta of
exactly the 33 leads. All filter 155 -> 122.

### Card now says which flow it is
`orderKind(job)` -> powercare | expense | quote (PowerCare wins when an order is
both, the plan covers the cost). Drives a QUOTE / SERVICE ACCOUNT / POWERCARE
badge and relabels the button Create Quote / Log Expense / Review PowerCare, so
Daniel does not have to open a card to learn what it wants.

## 2853f37: unworked orders can no longer sit in Billing's money columns

Live `v1.7.6.0+2853f37.1786213507990`, builtAt 2026-08-08T18:25:07Z. Verified
in the deployed `assets/Billing-DLg-exst.js`, where the minified selector now
reads `woStatus==="draft"?"new":woStatus==="quote_sent"?...` ahead of every
`status` test.

### Report
"SO-2605-48600 has not been completed and it is showing up in the invoiced
column. Please adjust this and review other cards in the same issue."

### Cause
`getBillingColumn` read the coarse `status` FIRST, so `status:'invoiced'` put a
card in Invoiced even when `woStatus` still said `draft`, i.e. never quoted,
never scheduled, never worked.

Swept the whole board for the class, not just the one card. Exactly three:

| SO | client | status/woStatus | total |
|---|---|---|---|
| WO-2605-48600 | Yadiel Huet | invoiced/draft | $180 |
| WO-2605-55497 | Tianna Brown | invoiced/draft | $125 |
| WO-2605-79732 | Derek Olinger | invoiced/draft | $180 |

`completedAt`, `invoicedAt`, `clientPaidAt` and `xeroInvoiceId` are ALL null on
all three. Nothing corroborates the invoiced claim. Two were last written
2026-06-12, the stale-push incident date, so `status` is the corrupt field and
`woStatus` is the truth.

A separate 13-card group looks similar but is FINE: `[invoiced/completed]` is
just woStatus lagging one step behind a real invoice. Do not "fix" those.

### Fix
woStatus is what the SO panel actually drives through the 8 stages, so the two
PRE-WORK stages are now tested before `status`:
```
draft -> new ; quote_sent -> quote_sent ; then paid/invoiced/completed ; then pending
```

**RULE: when two status fields disagree, the one the UI actually drives wins,
and the money columns are the ones that must fail closed.** A card wrongly in
Invoiced is a revenue number that is quietly wrong.

**RULE: measure the blast radius of a precedence change by REPLAYING both
orderings over live rows.** Replaying old vs new across all 118 live orders
returned exactly one transition group, `invoiced -> new`, n=3. That is what
made this safe to ship without hand-checking 118 cards.

### Trap worth remembering
Between two browser measurements the columns swung 13 -> 0 (Ready to Invoice)
and 34 -> 45 (Invoiced), which looked exactly like a regression I had just
caused. It was not: **23 orders had been touched in the last 2 hours by
another live user.** The SQL replay is what proved the code moved only 3 cards.
Do not diff two live snapshots of a multi-writer board and attribute the delta
to your change.

Scope kept: auto-return still works from every worked woStatus
(scheduled / in_progress / completed -> Ready to Invoice) and `status` is still
trusted once woStatus reports the work done.

### NOT done, needs an explicit decision
The three rows still carry the bogus `status:'invoiced'` in Supabase. The board
now renders them correctly, but the underlying data is still wrong and any
other consumer reading `status` will still see "invoiced". Repairing production
rows is a separate call, so it was left alone.

Build green, 472/472 tests (28 in billingColumns).
