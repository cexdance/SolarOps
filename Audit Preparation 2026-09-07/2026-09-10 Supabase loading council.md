# Supabase loading council

Read [[00 Current documentation guidance]] before this review. Evidence is local source inspection and mocked regression tests, not production latency measurements or a live database audit. This review owns the startup/session and loading portion of the broader council.

## Implemented locally

- **P1: fresh login never enabled core Realtime or immediately hydrated remote records.** The previous `src/hooks/useSyncEngine.ts:124-132,196` checked the session once during mount and exited when signed out. `src/App.tsx:1290-1316` subsequently accepted login without starting the core pull/subscription. The hook now observes authentication, starts a pull and one subscription on a new signed-in identity, and unsubscribes on logout/unmount. Repeated sign-in and token refresh events do not duplicate channels. Callback work is deferred to a timer so a pull's session lookup runs outside the Supabase auth callback lock. The restored-session lookup cannot override a newer auth event. Current implementation: `src/hooks/useSyncEngine.ts:133-239`.
- **P2: focus, reconnect and manual triggers could issue concurrent duplicate pulls.** A shared in-flight promise within the hook now coalesces ordinary triggers (`src/hooks/useSyncEngine.ts:64-105`). Login waits for any preceding pull and then requests a fresh authenticated one, because the old cycle may have captured no session. Deep sync waits before clearing the cursor, preserving full reconciliation after an incremental pull (`src/hooks/useSyncEngine.ts:266-272`). This does not coalesce App's separate startup `syncFromDB` path.

Validation: `pnpm exec vitest run src/__tests__/syncSessionLifecycle.test.tsx`: six passing mocked React hook tests covering fresh login, login racing an unfinished mount pull, duplicate auth events/logout, overlapping focus/online requests, full sync after incremental sync, and restored sessions/unmount cancellation. The first five tests were also run with the original HEAD hook temporarily restored under a try/finally guard: all five failed assertions. In particular, original login created zero channels and overlapping triggers issued three pulls instead of one. The modified hook was restored immediately afterward. `pnpm exec tsc -b` passed before the final small login-race guard; the main council owns the final combined build.

## Remaining findings requiring follow-up

1. **P1: startup timeout can overwrite the durable cache with boot defaults.** `src/App.tsx:680` initializes React using synchronous `loadData`; when data exists only in IndexedDB this yields defaults (`src/lib/dataStore.ts:460-471`). Initial `hydrateData` at `src/App.tsx:868` loads the in-memory store but does not adopt that result into React. If the remote pull lasts more than eight seconds, `finally` at line 890 enables persistence; the save effect at lines 921-925 writes the still-default React state after 500 ms. A later remote merge can therefore read the overwritten cache, particularly damaging for an incremental pull or unsynced local records. Adopt the local snapshot before starting the remote wait and gate persistence on successful local hydration, independently of remote readiness. Test an IDB-only cache and a remote pull resolving after the deadline.
2. **P1: the eight-second limit does not cover a hanging IndexedDB hydration.** The timeout is created at `src/App.tsx:824-826`, but `Promise.race` is only installed after `hydrateData` resolves (`868-879`). A stalled IDB open therefore leaves `dbReady` false indefinitely, and the timeout rejection initially lacks a handler. `src/lib/stateStore.ts:32-45` has neither an open deadline nor a blocked handler. Race the whole boot sequence or separately bound local initialization; keep writes disabled while local state remains unresolved. Test a never-resolving hydration promise. This is a distinct trigger from finding 1.
3. **P1: the startup photo merge resurrects remotely deleted photos.** `src/App.tsx:852-860` keeps the entire previous photo array whenever it is longer than the incoming array, whereas the polling hook uses `mergeWoPhotos` to preserve pending uploads while honoring remote deletions. Replace the count heuristic with the shared photo merge contract. Test a remote deletion while a separate local upload is pending.
4. **P2: successful pulls containing only standalone RMA/config changes are not adopted into React.** `src/hooks/useSyncEngine.ts:73-83` returns the old state whenever customers/jobs compare equal, even though `pullAndMerge` returns other changed state fields. Include all synchronized fields in change detection, or compare the intended updated slices explicitly. Test changed `standaloneRmas` with unchanged jobs/customers.
5. **P2: separate startup pulls duplicate work and retain an uncoordinated persistence path.** App starts `syncFromDB` at `src/App.tsx:870`, while the hook starts `syncNow` at `src/hooks/useSyncEngine.ts:113`. They use different local read/adoption paths and are outside each other's in-flight gate. After the startup hydration defects above are covered with tests, use one shared boot/poll coordinator that merges into the latest snapshot. Measure request count and time-to-local-data before attempting broader query optimizations.

The broader council also identified failed pulls being reported as successful and cursor advancement after incomplete pagination. Those paths are owned by the sync reviewer and are not certified by this note. Preserve contractor authorization, server clocks, field merges, tombstones, pending photos, and durable local changes when addressing the remaining items.
