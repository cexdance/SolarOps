## 44b772d - Move to Client double-click: root cause, fix, and Daniel Torres cleanup

Deployed and verified live (`sha: 44b772d`, `builtAt: 2026-09-08T13:12:49Z`).

### The incident
Daniel Torres became two clients, `US-15699` and `US-15700`, from one lead.

Timeline, UTC, reconstructed from the Apps Script execution log and the `cust-`
ids (which embed `Date.now()`):

| time | event |
|---|---|
| 12:48:29.329 | click 1, `doPost` #1 starts |
| ~12:48:31.3 | #1 returns `US-15699` (1.998s) |
| 12:48:32.272 | **click 2**, `doPost` #2 starts |
| 12:48:32.337 | click 1 finally creates the customer |
| 12:48:34.668 | click 2 creates the second customer |

Click 2 landed **65 ms before click 1 had created anything**.

### Root cause
1. **Primary, self-inflicted in e951907.** `handleConvertLead` was synchronous
   until the registry call was added; the panel closed on the same tick as the
   click, so a second click was impossible. Making it async introduced a 2-4s
   window in which the panel is visually unchanged and the button is still live.
   The operator concludes the click missed and clicks again.
2. **The dedupe cannot catch this by construction.** `findDuplicateCustomer`
   keys only on `clientId` / `solarEdgeSiteId`. Each click claims a *fresh*
   number, so click 2's `US-15700` can never match click 1's `US-15699`.
3. **Contributing.** `handleCreateCustomer` reads `data.customers` from the
   render closure. Its own comment predicted this exact case.

### Fix (44b772d)
`convertingLeadRef` (blocks same-tick re-entry) + `convertingLead` state, and
`disabled` + a "Claiming number..." label on the button. The ref is the guard;
the label is what stops the operator wanting to click twice.
Test: `src/__tests__/leadConvertReentry.test.tsx`, mutation-checked (removing
`disabled={converting}` makes it fail). Full suite 717 passed.

### Cleanup performed
- Keeper is **US-15700**: the job `job-trello-6a7628087e65c457a39df445` points at
  it and it carries the later real activity. `US-15699` was an orphan whose only
  unique activity entry was the system audit line from its own creation.
- Backed up to `_bak_torres_dupe_20260908` (**RLS enabled**), tombstoned in
  `deleted_customer_ids` (985 entries), then the `customer:` row deleted.
  Tombstone written BEFORE the delete so a stale tab cannot resurrect it.
- Sheet cell `C686` cleared, so `US-15699` is free and is the next number the
  registry will issue. No gap in the sequence. 767 numbers, zero duplicates.

### Patterns worth reusing
- **Making a handler async is a re-entrancy change**, even when the logic is
  untouched. Any button whose handler gains an `await` needs a disabled state in
  the same commit, or you have built a double-submit.
- **Verify the row index against the data, never against a screenshot.** I had
  `US-15699` at row 685 by counting; it is row 686. The header plus a tall blank
  row 2 shift everything. A guarded read before the write catches this.
- **The clipboard is not yours.** A `pbcopy` was silently replaced by an
  unrelated URL between copy and paste, and `cmd+a` + `cmd+v` wiped the whole
  Apps Script buffer. It was unsaved, `cmd+z` restored it. Never blind-paste
  into an editor holding the only copy of something; verify what landed.
- **A `toContain('disabled')` assertion on Tailwind markup is a false pass**:
  the class `disabled:opacity-60` contains the substring. Assert on the
  `disabled=""` attribute inside the specific opening tag.

### Open follow-ups

  David McLauhglin `US-15263/4`, Anthony Client `US-15610/1`, Grif Blackstone

## df88bc0: SOW report shows every photo category, PDFs get their own page

**What changed and why.** The SOW distribution report (the customer/office facing
service order report) was rendering only 5 of the 14 photo categories. Its own
`PHOTO_CATEGORIES` array listed `before, after, process, serial, parts`, while
`PHOTO_CATEGORY_LABELS` right below it defined all 14. Everything the field

Old/New Cabinet and Wall Overview was collected, stored, counted in the panel,
and then silently dropped from the report.

PDF attachments were filtered out of the report entirely, by an explicit filter
whose comment said they "can't render as an `<img>`". True, but the fix is a
different element, not deletion. They now split into their own list and each one
gets a full page: filename header plus an 80vh iframe, with
`break-before: page` in the print stylesheet.

**Files modified:** `solarflow-dashboard/src/components/SowDistributionModal.tsx`

**Pattern worth reusing.** A render list that is a hand-written subset of a
labels/config map next to it will drift the moment someone adds a category. The
labels map is the source of truth; the subset was a snapshot of it from whenever
the report was written. When two adjacent constants describe the same enum and
one is shorter, the short one is usually stale, not deliberate.

**Verified:** `pnpm build` green, `pnpm test` 742/742 across 80 files.
Live `version.json` = `v1.7.6.2+df88bc0.1788907069824`, `builtAt`

the serverless functions built.

**Follow-ups:**
- Browsers do not print the content of an embedded PDF. On paper each PDF page
  is an identified placeholder (filename header), not the document itself. If
  printed PDF pages are ever actually required, merge them server-side. Marked
  with a `ponytail:` comment at the render site.

## 530b974 - a conversion that aborts after claiming must give the number back

Deployed and verified live (`sha: 530b974`, `builtAt: 2026-09-08T22:51:29Z`).
Registry Apps Script deployed as **Version 3**; the `/exec` URL is unchanged.

### The incident
Taylor Williams held two registry rows. Two `doPost` calls, 18:06:56 and
18:07:48, **52 seconds apart**, and only ONE `customer.create` in `change_log`
(22:07:50 UTC). So this was NOT the 44b772d double-click: that guard held, and
one customer was created. Two separate conversion attempts, the first of which
claimed a number and then aborted.

### Root cause
`claimClientNumber` is a WRITE. `convertLead` called it FIRST and only then ran
its own checks, and the `clientNumberOwner` abort `return`s without giving the
number back. So attempt 1 stamped the name onto a row, bailed, and told the
operator to try again. The retry claimed the NEXT number.

**RULE: if a remote call allocates a resource, every abort path after it must
release the resource. Ordering a write before your own validation turns each
failed validation into a permanent leak.**

### Fix
- `doPost` takes `op:"release"`. It clears a row ONLY when the row still holds
  exactly the name it was told to expect; otherwise it is a no-op that reports
  who actually holds it. Verified live in both directions before use: a wrong
  name returned `released:false, reason:"row no longer holds that name"` and an
  unknown number errored.
- `releaseClientNumber()` in `clientRegistry.ts`, best effort, returns whether
  the number came back.
- `convertLead` releases on the `clientNumberOwner` path and states in the alert
  whether it succeeded, so a failed release cannot pass silently.
- Only a number this call MINTED is released. One the lead already carried is
  not ours to hand back.

Build green, 747 tests pass.

### RULE: change_log has no duration column, so time is INFERRED

Events are grouped into sessions with a 30-minute idle gap and each session
counts its first-to-last span. The gap was measured before it was chosen:
across 60 days, 91.9% of gaps between consecutive events are under 5 minutes
and the curve is flat from 15 to 60 minutes (94.4% at 15, 95.7% at 30, 97.1%
at 60), so the totals barely move if it is retuned. A lone event gets a
5-minute floor rather than zero.

Day totals are summed per person rather than one span across the window. A
naive first-to-last span would absorb every overnight gap into working time
and report over 24 hours for two days of light work. There is a test pinning
exactly that.

### RULE: `change_log.user_email` is NOT a person, group on `actor_uid`

`contractor-N` is a reusable SLOT label, not an identity:
- `contractor-4` and `Jaime Mendez` share `actor_uid` dc694b73, one human.
- `contractor-2` is `actor_uid` 0476e52e, which is **Cesar's own account**.

So grouping by the email string credits an admin's work to a contractor. The
widget keys on `actor_uid` and only falls back to the email when it is null
(6,591 older rows have no uid). Bots excluded: `system`, `unknown`,
`recovery-script`, `claude-repair-script`.

### RULE: a permit gate on a `users.find(id)` lookup silently DENIES

The gate first denied an admin. `hasPermit` treats admin as a superuser, so
the cause was the lookup: `currentUserId` is not guaranteed to match a row in
the `users` array, the find returned undefined, and `hasPermit(undefined)` is
false. Fixed by passing `currentUser` down from App (`data.currentUser`)
instead of re-deriving it.

**⚠ `AddressCleanupWidget` and `DeepSyncMetricsWidget` use that same
`users.find(u => u.id === currentUserId)?.name || 'Unknown'` lookup** and are
falling back to "Unknown" for the same reason. Cosmetic there, but the same
latent bug. Not fixed in this commit.

### Why the widget is gated at all

RLS on `change_log` is `team_read` / `is_staff()`, so **every staff user can
already read everyone else's activity**. A widget that ranks named colleagues
by hours worked is a different exposure from a raw audit table, so it is
gated on the `users.manage` permit (admin holds it; sales, support and coo do
not by default). The gate is in the app because RLS cannot express it.

Added `permit?: Permission` to `WidgetCatalogEntry`; the Add Widget picker
filters on it, and the render switch re-checks so a persisted layout cannot
smuggle it past the picker.

### GOTCHA: never select `change_log.payload` from the client

Payloads carry whole customer records with `activityHistory` and file arrays,
tens of KB per row. The widget selects only
`user_email,actor_uid,created_at,op_type` and pages 1,000 rows at a time.

### Honest limits, stated in the UI

Estimates measure **writes to SolarOps only**. Calls, site visits, email and
reading produce no events, so someone in the field all week looks idle. The
widget says "estimated" with the method in a tooltip. It is a floor, not a
timesheet, and should not be used as a pay input without that caveat.
