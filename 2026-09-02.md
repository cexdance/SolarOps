## 3e7592b: SolarEdge site-transfer autofill + case number capture

Live at v1.7.6.2+3e7592b, verified against `version.json` and a real `/api/users`
(401 JSON, not a Vercel NOT_FOUND).

### What changed and why

Daniel asked to automate submitting the SolarEdge site transfer at
`https://www.solaredge.com/site-transfer`. A server-side submission is not
possible, and the reason matters more than the feature:

1. **The page is behind a Cloudflare bot check.** The in-app automation browser
   sits on "Just a moment..." forever and never gets the form. The user's real
   Chrome loads it in about 5 seconds. Getting a headless client through would
   mean defeating bot detection, which is out of bounds.
2. **The form is a Drupal wizard with a per-session token.** Only Customer
   Number renders on load; the other 33 fields exist in the DOM but are hidden
   until it validates, and the POST carries `form_build_id` / `form_id`. A blind
   POST fails even setting Cloudflare aside.

So the fill happens inside the operator's own browser, via a bookmarklet.

### Patterns worth reusing

- **RULE: when a target site is behind bot detection, that is the design
  constraint, not an obstacle to route around.** The whole shape of this feature
  (bookmarklet in the user's browser, never a server POST) falls out of that one
  fact. Establishing it took two minutes and saved building the wrong thing.
- **RULE: an idempotent re-runnable action beats detecting the step.** The form
  reveals fields progressively. Rather than model the wizard, the bookmarklet
  fills everything currently visible and you click it again. Fewer moving parts
  and it cannot get out of sync with a page we do not control.
- **RULE: the id belongs to the SLOT, not the value** (same family as 09-01
  a268edc). The RMA entry id is `rma-sitetransfer-<jobId>`, so clicking Submit
  twice reuses one entry instead of stacking duplicates.
- **The bookmarklet never submits.** Fill-only means the payload is always
  reviewed by a human before it goes. Deliberate, not a limitation.
- **GOTCHA: `cd` persists between Bash calls in a session.** `mkdir -p public`
  landed in `solarflow-dashboard/src/public/` because an earlier `cd public` was
  still in effect. Use absolute paths for mkdir.
- **GOTCHA: vitest `include` is `src/__tests__/**/*.test.{ts,tsx}`**, not the
  `*.test.ts`-anywhere the memory index claimed. A test outside that directory
  exits "No test files found", which reads like a pass.
- **GOTCHA: `new URL(path, import.meta.url)` throws "The URL must be of scheme
  file" under vitest.** Use `resolve(process.cwd(), ...)` to read a fixture.
- **TRAP: I read a stale rtk tee log and reported a passing test as failing.**
  Piping vitest to `/dev/null` left the previous run's JSON as the newest log.
  Re-run and read the run's own output.

## dfdd005: the install page's own button was a trap

Reported immediately after the deploy: clicking **SE Transfer Fill** on the
install page (instead of dragging it to the bookmarks bar) ran the bookmarklet
against the install page, which has no site-transfer form. It fell into the
generic no-form branch and dumped the install page's own text back as "copy it
by hand from: SolarEdge site transfer autofill Drag this button...".

- **RULE: a bookmarklet's install page is the first place it will be run by
  mistake, so it is the first case to handle.** A draggable `javascript:` link
  is also a clickable one, and nothing about it signals which gesture is meant.
- Fix: the page carries `id="se-transfer-install-page"`, which the bookmarklet
  checks before anything else and answers with the drag instruction. Done in
  the bookmarklet rather than a click handler on the page, because the site CSP
  governs inline script and a `javascript:` href cannot be intercepted without
  one. Copy also now says drag it UP, warns against clicking, and gives
  Cmd+Shift+B for a hidden bookmarks bar.
- **GOTCHA: editing `public/site-transfer-autofill.js` does NOT update the
  page.** The `javascript:` href is a minified copy embedded in the HTML and
  must be regenerated, the same shape of trap as the Apps Script deploy step.
  Worth a build step if this is edited again.
- Test count 675. The guard has its own check, asserting the drag message
  appears and the copy-by-hand fallback does not.

## 674d177 - Billing list view filters by billing stage

**Commit:** `674d177` feat(billing): filter the list by billing stage, not by a 4-way status guess
**Live:** verified, `version.json` sha 674d177 built 16:12 UTC, `assets/Billing-D9kgmPkA.js` carries the new string, `/api/users` returns a real 401 JSON.

### What was wrong
The Billing list view was not missing filters, it was filtering by the wrong vocabulary. The list only had the coarse `all / unbilled / invoiced / paid` dropdown, which cannot express "Ready to Invoice" or "Costs Covered", the two stages the board actually runs on. Result: one undifferentiated 151-row scroll sitting next to a kanban that sliced the same records seven ways with `getBillingColumn`.

### What changed
- `BILLING_COLUMNS` hoisted to module scope in `Billing.tsx`. The kanban columns and the list stage filter now read from one array, so a renamed stage is renamed in both places.
- Stage chips with live counts above the list, persisted to `solarops_billing_list_stage`.
- The coarse status dropdown is hidden in list mode. Two status controls on one toolbar is how a user filters themselves into an empty screen with no idea which control did it.
- `matchesSearch` extracted from the inline filter chain so list and kanban share the search predicate (the empty-query guard from 08-24 c0bfdee is preserved verbatim).
- Empty state names the stage and offers "Show all stages".
- Active chip is a solid stage-colored fill, not a pastel tint.

### Patterns worth reusing
- **RULE: when two views of the same records disagree on their filter vocabulary, the one with fewer categories is usually the broken one.** The kanban had 7 stages, the list had 4 statuses, and the 4 were not a coarsening of the 7, they were a different axis. Adding filters to the list would have been the wrong fix; adopting the kanban's axis was the right one.
- **RULE: counts that do not sum are a trust bug on a money screen.** First build shipped All (151) against stages summing to 127. Archived orders counted in All but belonged to no stage. 24 orders silently unaccounted for. Archived is now excluded from All too. **Always add up the counts you put on screen before shipping them.**
- **GOTCHA: an active state tinted in the stage's own pastel can be weaker than another chip's hover state.** The slate "Pending Completion" active chip was indistinguishable from a hovered inactive chip. Solid fill for selection, tint for nothing.
- Verification caught both of the above, not the diff. Screenshots of live data, not the code, are what showed the numbers not adding up.
