
## 8a58a53 + edge fns (callback v9, site-transfers v7) - Xero 403 on the site-transfer button

**Symptom:** button returned `Xero GET /Contacts -> 403 AuthenticationUnsuccessful`. `xero_auth`
showed the token refresh had SUCCEEDED 90s earlier and the stored org was Conexsol.

**Why that combination is possible:** a refresh can succeed while the ORGANISATION is no longer
connected. The grant belongs to the Xero user; the connection belongs to the org. Xero then
answers every API call with a bare 403.

**Fix:** `getAccess` checks `/connections` after refreshing. If the stored org is missing it
names it, lists what IS connected, shows the token's granted scopes, and gives the
`?force=1` link. Any 401/403 now carries the granted scopes. The callback stores the org picked
in THIS consent (token `authentication_event_id` == connection `authEventId`), not `conns[0]`,
which can be a stale or different org.

**Xero granular scopes (from 2 March 2026):** apps created after that date have NO
`accounting.transactions`. Use `accounting.invoices` (ACCREC + ACCPAY), `accounting.payments`,
`accounting.settings.read`. All verified against the authorize endpoint.

**DRIFT CAUGHT BEFORE IT SHIPPED:** earlier deploys were assembled by hand in the deploy call,
so the local files lacked four live changes (TAX_TYPE default NONE, invoice try/catch, account
hint, and `?force=1` on the callback). Deploying the local copy would have silently reverted
them, including breaking the re-auth link the user had just been given.
**RULE: deploy edge functions FROM the local file, never from a hand-assembled copy.** Grep
the local file for every live marker first; syntax-check with esbuild; then deploy verbatim.

Regression-checked live: anon 403, preflight allows x-client-info, no-force shows "Already
connected", `?force=1` redirects with granular scopes and Xero accepts them.

**Next:** user re-authorises with `?force=1`, then presses the button. If it still fails the
message now says exactly which org and scopes are involved.

## "Send to Trello" on service orders (b36e78d, c60bbc2)

**Request (user):** a new customer is logged in SolarOps, but Anthony works
only in Trello and needs a card there to follow up on the RMA and the order.

**What shipped:** a "Send to Trello" button beside Labels on the SO panel.
It opens a picker of the Florida board's open columns (preselects the order's
own column, else "Needs follow-Up Service") and previews the card title
(`US-15700 Taylor Williams`, the board's own convention). The card carries
SO number and service, status, client number, contact, address, the REAL site
id, inverter serial, each RMA from the panel's LIVE list (part, RMA no., case,
status) and the first 1200 chars of notes; empty lines are omitted. Once sent,
the button is "Open in Trello". Files: `api/trello-card.ts`
(`handleCreateCard`, `refJobId`, `linkedJobFor`), `lib/trelloSync.ts`
(`soCardContent`, `defaultListFor`, `sendServiceOrderToTrello`),
`components/SendToTrello.tsx`, `ServiceOrderPanel.tsx`, `types/index.ts`
(`trelloCardId`, `trelloCardUrl`).

**The trap it had to avoid:** that card is not a lead. The webhook imports any
card created in any list (b0e4d0d), so it would import a duplicate of an
existing customer and ping 7 office phones, and the nightly sweep would
re-import it every night. The server writes `SolarOps ref: <jobId>` as the
card's last line, INSIDE the card from its first moment, so the very first
webhook delivery (often before the app has saved the link) already knows.
Webhook and sweep skip a card by that line OR by a `trelloCardId` saved on an
order, so deleting the line in Trello does not turn it into a lead.
`refJobId` refuses a lead's own id, and the server strips any ref line the
client sends. **RULE: when a system you write to echoes your write back as an
event, put the link in the object at creation, not in a follow-up write.**

**Verified on production (not simulated):** 401 unauthenticated; 400 for an
archived list; 409 for a lead id; a created test card carried exactly one
ref line (a spoofed one in the body was stripped); 0 lead jobs and 0
notifications after creation AND after moving it to another list; the sweep
imported 0 with it open. Test card `6aa436167c8ea4004d2d67ab` archived
(not deleted).

**Caught in the UI capture:** the picker was left-anchored and the panel
clipped its right half; fixed with `right-0` (c60bbc2).
