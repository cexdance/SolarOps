### The echo-loop trap (worth reusing)

Bidirectional label sync ping-pongs forever if the two sides spell a label
differently. The live board has **`First Contact – Call Completed` with an EN
DASH**; `LABEL_CATALOG` uses a hyphen. Compared raw, each side reads the other
as changed and mirrors back, forever. `sameLabelSet()` compares by `labelKey()`,
duplicated server-side because `api/` cannot import from `src/`; a test pins the
two normalizers to each other. **RULE: a bidirectional mirror is only safe when
its equality test is the same normalization both writers use. Set equality, not
array equality: order and colour are not identity.**

### Changed

- `PATCH /api/trello-card` generalised from labels-only to a card push:
  `{ cardId, stage?, name?, labels? }`. **Only the fields sent are written**,
  which is what makes it safe to call on every save: a kanban drag cannot
  rewrite the card's name or labels as a side effect. One `PUT` carries a move
  plus a relabel, so Trello fires ONE `updateCard` back instead of two.
- **`STAGE_LISTS` is built by inverting `LIST_STAGES`**, never written out a
  second time, so the two directions of the mirror cannot drift. A test
  round-trips **every** entry of `PIPELINE_STAGES` through both maps. **RULE:
  an unmapped column does not error, it silently stops mirroring, and you find
  out days later when Trello is wrong. Assert the round trip, not the map.**
- **Name is pushed ONLY over a placeholder filename.** Anthony's cards arrive
  named `image.jpeg` because Trello fires `createCard` before the attachment
  lands, so naming them is the most useful thing this push does for him, and
  overwriting a name he typed by hand is the worst thing it could do. The
  client sends `clientName`, never `title`: `title` becomes `WO, <name>` on
  conversion, and pushing that would rename his card to internal jargon.
- **Hooked into `App.handleUpdateJob`, the single save choke point**, replacing
  the two per-control hooks from fc48079. Every LL edit path (kanban drag,
  LeadPanel, ServiceOrderPanel) already funnels through it, so one call covers
  all three and a control added later mirrors for free. **RULE: hook a mirror
  at the save path, not at the widgets, or the mirror's coverage is a list
  someone has to remember to extend.**
- `cardPatchFor(prev, next)` is pure, exported and tested. It returns
  `undefined` for the common case (costs, photos, scheduling), which is what
  keeps this off the ~95% of saves that have no card representation.

### Echo-loop analysis (all four paths terminate in one round trip)

1. Drag to a NON-target list -> `PUT idList` -> `updateCard` w/ `listAfter` ->
   backfill computes the stage already on the job -> `stageChanged` false ->
   no write.
2. Drag INTO a target list (`leads`, `lost_to_competition`) -> `matchTargetList`
   matches -> `upsertLeadJob` returns `'exists'` -> reconcile backfill with the
   same stage -> no write. **`notified` is 0 because notification fires only on
   `'created'`,** so pushing a card into the Leads list from LL cannot spam the
   office.
3. Label push -> whole-set mirror returns the identical set -> no write.
4. Name push -> `job.clientName` is no longer a placeholder -> `nameChanged`
   false -> no write.

## 8e2eb97 - One level of undo (+ the concurrent site-transfer landing)

Deployed: v1.7.6.2+8e2eb97.1788471738511, builtAt 2026-09-03T21:42:18.511Z.
`/api/users` returns 401 JSON (functions built, not a NOT_FOUND page).

### What shipped

`solarflow-dashboard/src/lib/undo.ts` (new). A single in-memory slot holding the
PREVIOUS version of only the records a mutation touched, diffed by id across
`customers` / `jobs` / `standaloneRmas`. 60s TTL, cleared on logout and reload.

The design decision that matters: **it is NOT a whole-AppState snapshot.**
Restoring the blob would also revert anything a teammate's edit merged in between
the mutation and the undo, and because `pushToSupabase` is dirty-tracked per
record, every record that differed would go dirty and push back over theirs.
`applyUndo` splices the slot's records into the CURRENT state, so untouched
records pass through. There is a test for exactly this.

**Tombstones were the real work.** `pullFromSupabase` UNIONs the remote
`deleted_customer_ids` / `deleted_job_ids` into the local lists on every poll, so
clearing a tombstone locally alone is undone by the next 30s tick and the restored
record vanishes again. `clearUndoTombstones` drops the id locally AND pushes the
shortened list via `pushKeyValue` before the restore lands. New
`unmarkCustomersDeleted` / `unmarkJobsDeleted` in `dataStore.ts`.

12 handlers wired: create/edit/delete WO, create/edit/delete customer, merge
customers, create/edit standalone RMA, SolarEdge sync, Florida sites, import apply.
The three bulk ones are the best of the batch: one undo reverts a whole import
because it is one `setData`.

UI: sonner `toast` with an Undo action (sonner and `<Toaster/>` were already
installed and mounted), plus Cmd/Ctrl+Z that bails inside INPUT/TEXTAREA/SELECT/
contentEditable so the browser's own text undo keeps working.

### Patterns worth reusing

- **A single `useState<AppState>` root plus a uniform `setData(prev => {...;
  saveData(next); return next})` shape is what made this cheap.** One line per call
  site, no new sync code, undo rides the existing dirty-tracked push.
- **Undo scoped to touched records, never to whole state.** In any LWW app, a
  whole-state restore is a mass clobber wearing a friendly label.
- **A half-undo that silently re-applies itself is worse than no undo.** The three
  contractor handlers (`handleContractorJobUpdate`, `...ProposeSchedule`,
  `...ReportAdditionalItem`) write the contractorJobs blob AND mirror into the admin
  Job; undoing only the admin half would be re-mirrored on the contractor's next
  save. Deliberately not wired, with a comment at the handler saying why.
- **Announce, do not toast, from inside a `setData` updater.** StrictMode
  double-invokes it. `markUndo` dispatches `solarops:undo-armed`; App listens and
  toasts with a fixed id, which collapses the double-fire AND makes a new mutation
  replace the old offer, which is what a single-slot undo should look like.
