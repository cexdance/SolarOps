## 223ac66 - CSP blocked the client registry write ("Failed to fetch")

**Symptom:** "Move to Client" on a lead alerted `Could not update the client registry sheet: Failed to fetch. Nothing was converted.`

**Cause:** `claimClientNumber()` (`solarflow-dashboard/src/lib/clientRegistry.ts`) POSTs to the Apps Script `/exec` URL, but `vercel.json`'s `connect-src` never listed `script.google.com`. The browser killed the request before it left, so the `catch` reported a network error and correctly aborted the conversion. Nothing wrong with the script or the sheet.

**Fix:** added `https://script.google.com https://script.googleusercontent.com` to `connect-src` in `vercel.json`. Both hosts are needed: `/exec` 302s to `script.googleusercontent.com`.

**Files:** `vercel.json`

**Verified:** prod `version.json` sha = 223ac66, the live CSP header contains `script.google.com`, `/api/users` still 401s (functions built).

**Pattern worth reusing:** a third-party host added in code needs a matching `connect-src` entry, or it fails only in prod. `vite dev` sends no CSP header, so this class of bug is invisible locally. Same family as the 05-01 `recompressDataUrl()` CSP no-op.

## f3a1ba2 - production report emailed as plain text instead of the HTML report

**Symptom:** the client received an email whose whole body was "Please view the attached HTML report for your solar production summary. - Conexsol Service Team". No report, no attachment.

**Cause:** `handleSendReport` in `Customers.tsx` reads the SMTP password from `sessionStorage`. Settings wrote it there too, so it was gone in every new tab. With no password the send fell through to a `mailto:` fallback, and a `mailto:` body is plain text by spec, so the HTML report could never ride in it. The fallback's hardcoded sentence is exactly what the client saw. The SMTP path itself (`api/send-report.py`) was fine all along: it already attaches the full HTML as a `text/html` MIME part.

**Fix:**
- `Settings.tsx` - SMTP password now persists in `localStorage`. Reads fall back to the old `sessionStorage` value once so nobody retypes it; Clear removes both keys.
- `Customers.tsx` - same read order on the send path.
- `Customers.tsx` - deleted the `mailto:` fallback. Missing credentials now set `sendError` ("Email password not set for this session...") instead of opening a compose window that cannot carry the report.

**Files:** `solarflow-dashboard/src/components/Customers.tsx`, `solarflow-dashboard/src/components/Settings.tsx`

**Pattern worth reusing:** a silent fallback to a *less capable transport* is worse than an error. The send "succeeded" every time, so the failure only surfaced when a client mentioned the email looked empty. If path B cannot carry the payload path A carries, it is not a fallback, it is a bug with a friendly face.

**Second pattern:** `sessionStorage` for a credential means the feature silently degrades once per tab. Pick the storage lifetime to match the feature's lifetime, or make the missing-credential case loud.

**Tradeoff accepted by the user:** the SMTP password is now plaintext in `localStorage`, readable by any script on the origin. Upgrade path is recorded in a `ponytail:` comment at `Settings.tsx:136` - move the credential server-side per user.

**Follow-ups:** none blocking. No visual change shipped, so `/snap-ui` was skipped.

## b9ea98e - Xero: admin button creates the client and drafts the site-transfer invoice

Live: `v1.7.6.2+b9ea98e.1788285405064`, builtAt 2026-09-01T17:56:45Z. `/api/users` returns
`{"error":"Unauthorized"}` (401 JSON, not a NOT_FOUND page), so the functions built.

### Why
Daniel opened every Xero draft one by one to work out which SO it belonged to, then
hand-created the customer before he could invoice a site transfer. One button now does the
client creation.

### Architecture: the agent is standalone, on purpose
A partner vetoed connecting Xero to SolarOps. Two Supabase edge functions own the Xero OAuth
instead. SolarOps never holds the credentials and has no Xero code path of its own.
Credentials live in Supabase secrets; `xero_auth` has RLS ON with ZERO policies, so only the
service role reads it.

- `supabase/functions/xero-oauth-callback/` - ONE url does both halves of the handshake.
  No `?code` -> 302 to Xero consent. With `?code` -> exchange, store, done. The link Daniel
  clicks IS the registered redirect URI, so the two cannot drift apart.
  **Must deploy with `verify_jwt: false`**: Xero's redirect carries no Authorization header
  and would otherwise 401 with nothing obviously wrong on Xero's side.
- `supabase/functions/xero-site-transfers/` - contact + DRAFT invoice. `verify_jwt: true`.

### Rules worth reusing
- **Xero rotates the refresh token on EVERY use and kills the old one immediately.**
  Persist the new one BEFORE doing anything else: a crash between use and write-back leaves
  the connection dead and needs a manual re-authorisation. Tokens also expire after 60 days
  idle, which is why this runs on a schedule and NOT on Daniel's Mac. A sleeping laptop
  locks itself out.
- **"Has a valid JWT" is NOT authorisation.** The anon key is a valid JWT and ships inside
  the public frontend bundle. `verify_jwt` checks the signature, never WHO. Gate on the role
  claim: `service_role` -> the schedule, `authenticated` -> role must come from `user_roles`,
  anon -> denied. Verified live: anon 403, no token 401, garbage 401.
- **Idempotency from the REMOTE system, not new local state.** Contact looked up by
  `ContactNumber == clientId`, invoice by `Reference == woNumber`. Nothing written back onto
  the Customer record, which syncs whole-record LWW and would let a stale client clobber it.
  Pressing the button twice is safe.
- **A button press that quietly does nothing is worse than an error.** Ineligible jobs return
  a reason: "not a site transfer", "no order number, so this is not a service order",
  "already invoiced".
- **A half-configured integration should do the half it can.** The invoice stays dormant
  until `XERO_SITE_TRANSFER_ACCOUNT_CODE` and `_TAX_TYPE` are set. Guessing a tax code
  misstates the books, which is worse than not automating.

### Live-data findings that changed the design
- **There is no "opens the SO to invoicing" moment.** `getBillingColumn` puts a site transfer
  in `to_invoice` FROM CREATION (Billing.tsx:42-46, deliberate: "no quote and no field work").
  The trigger fires early by necessity.
- **`siteTransferCompletedAt` is unusable as a gate**: set on 3 of 11 site transfers ever and
  on ZERO of the currently-uninvoiced. Gating on it means the agent never fires.
- Of the 2 pending site transfers, **one has no `woNumber`** (US-15017 Parque Solar Doral).
  Since `isServiceOrder(job) = !!woNumber` it is not an order, and the filter excludes it.
- That same customer's `name` is literally `"US-15017 Parque Solar Doral"`, id baked in. The
  id goes in ContactNumber, so `cleanName()` strips it. Test: `cleanName.test.mjs`, 6 cases.
  A name that is ONLY the client id cleans to empty and the record is skipped.
