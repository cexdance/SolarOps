# 2026-08-25

## Service Orders board redesign (05046d9)

Shipped a full layout rebuild of the admin Service Orders kanban, drafted first
as a design canvas and then implemented in `Jobs.tsx`.

**Live:** v1.7.6.2+05046d9, builtAt 2026-08-25T04:06:35Z. `/api/users` returns
401 (not a Vercel NOT_FOUND page), so the serverless functions built.

### What changed and why

Five concrete problems, all visible in the pre-change catalog screenshot:

1. **Columns were `flex-1 min-w-[280px]`.** flex-grow stretched four columns
   across the viewport and clipped the fifth at the screen edge. Now a fixed
   `w-[218px] shrink-0`: five columns visible at 1440, the rest scroll.
2. **The control bar was three stacked rows** (view toggles / filter row /
   search) costing ~214px before the first card. One row, 52px. The board now
   starts about 130px higher, roughly one more card per column.
3. **Cards carried four colored pills with no hierarchy** (status, quote,
   priority, equipment). Priority is now a dot, work type and assignee are
   monochrome glyphs, PowerCare is a bolt beside the order number, and the
   single status pill is the only badge left.
4. **Names and addresses clipped mid-word.** The badge stack moved off the right
   rail onto the identity row, which freed the full card width, so `truncate`
   became a two-line `line-clamp-2` with `overflow-wrap: anywhere`.
5. **`Sort: Default` was repeated in every column header** (7 copies on the
   board, 14 on LL). One board-wide sort now drives the list view and every
   column; `columnSortBy` state is gone entirely.

Also: Hold/Resume became icon-only PauseCircle/PlayCircle buttons with the name
in `title` + `aria-label`, and the three filter toggles became icon+count chips
named On Hold / PowerCare / Archive.

### Patterns worth reusing

- **`formatMoney` is a policy gate, not a formatter.** With `SHOW_MONEY` off it
  returns `-`, so the card footer had been rendering a bare dash on every card
  for as long as the flag has been off. It now renders only when the value is
  real. This is the third time this gate has bitten; see the Billing notes.
- **A `//` comment cannot live inside a JSX opening tag.** Caught before the
  build, but it is a silent-looking edit that breaks the parse.
- **Raw markup cannot pass through a Design Component `{{hole}}`** (holes render
  as escaped text). Bind a single SVG `d` path string to an attribute instead.
  Relevant to the canvas, not the app.
- **Verify a board change against the capture script, not by reasoning.** The
  first pass looked right in code and had three real defects in the screenshot:
  the sort control had wrapped to a second row (defeating the whole point of the
  change), order numbers broke across two lines, and the meta row truncated.
  All three were only visible in the PNG.

## a0ec6a7 - authorization moved off user_metadata (Supabase lint 0015)

**What was wrong.** All 4 policies flagged by `0015_rls_references_user_metadata`
gated on `auth.jwt() -> 'user_metadata' ->> 'role'`: `app_data.team_read`,
`team_insert`, `team_update`, and `change_log.team_read`. `user_metadata` is
writable by the end user via `supabase.auth.updateUser`, so any contractor could
set `role='admin'` on themselves and read or overwrite all 612 customer/job rows
and all 18,147 change_log rows straight through PostgREST. The 08-23
`app_data_contractor_row_isolation` work closed the *authenticated-but-
unauthorized* hole; it left the role claim itself forgeable.

**Fix.** `public.user_roles (user_id PK -> auth.users, role, permissions text[])`,
RLS enabled with **zero policies** and client grants revoked, read through
`public.is_staff()` (`stable security definer`, `search_path=''`,
`(select auth.uid())`). All 4 policies rewritten `TO authenticated`.

**Three things found in the same pass that were not in the lint:**

1. **The old predicate FAILED OPEN.** It was `role <> 'contractor'`, so the 2
   accounts with no role at all (`cesarajurado@gmail.com`,
   `pentest_probe2_donotuse@mailinator.com`) had full staff access to every
   customer record. `is_staff()` fails closed. User chose "deny both".
2. **`api/users.ts` had the same bug one layer up, and RLS could not fix it.**
   `verifyCaller()` read `role` AND `permissions` from `user_metadata`, and
   `canManageUsers()` gated POST/PATCH/DELETE on that. Anyone could self-grant
   `users.manage`, then create admin accounts, re-role staff, or delete users.
   Now reads `public.user_roles` and mirrors writes into it; metadata is a
   display copy only. `permissions` had to move to the table too, otherwise
   self-granting the permit alone reopened it.
3. **`technician` was in the API's `STAFF_ROLES` but absent from `is_staff()`.**
   Zero exist today, which is exactly why nobody would notice: the first one
   created would silently see no data. Under the old policy they had access, so
   excluding them was a silent narrowing. Added.

**RULES worth keeping.**
- **A `<>` predicate on a role fails OPEN.** Every value that is not the one
  named string passes, including empty, null-coalesced, and typo'd. Enumerate who
  is allowed (`is_staff()`), never who is denied.
- **Fixing an RLS policy does not fix the API that shares its logic.** The
  database fix was complete and the escalation path was still fully open through
  `/api/users`, because that endpoint holds the service-role key and bypasses RLS
  by design. **Grep the claim (`user_metadata`), not the table.**
- **Supabase default privileges grant anon + authenticated full DML on any new
  public table.** RLS-with-no-policies still blocks them, so it is invisible, but
  the trusted table was one accidental `create policy` from being client-writable.
  `revoke all ... from anon, authenticated` on any authorization table.
- **A `SECURITY DEFINER` function in `public` is exposed as an RPC endpoint** and
  `revoke ... from public` does NOT remove the direct grant Supabase gives `anon`.
  Needs an explicit `revoke execute ... from anon` (the advisor flagged it).
- **Verify RLS by row count, not by UI.** A denial returns 0 rows with
  `error === null`. Impersonate in a transaction:
  `select set_config('request.jwt.claims', <json>, true); set local role authenticated;`
  (`set local` will not take an expression, so it has to be `set_config`).
- **Do not `count(*)` across a `lateral unnest`.** It counts permits, not users.
  Read support as 4 users when it was 2, briefly looked like the seed had
  invented rows.

**Verified live before reporting:** contractor holding forged
`user_metadata.role='admin'` sees 0 sensitive rows / 169 KV rows / 0 change_log;
role-less account identical; admin sees all 781; anon 0; contractor INSERT into
`customer:%` raises 42501; `user_roles` SELECT as authenticated raises 42501;
advisor no longer reports 0015. Deploy confirmed by `version.json` = a0ec6a7 plus
`/api/users` returning 401 rather than a Vercel NOT_FOUND.

**Files:** `supabase/migrations/20260825_app_data_role_from_table.sql`,
`supabase/migrations/20260825b_user_roles_permissions.sql`, `api/users.ts`.
No UI change, so no `/snap-ui`.

**Follow-ups.** (1) `App.tsx` still routes the UI off `user_metadata.role`; that
is display-only now and stays in sync because PATCH mirrors it, but the two can
disagree, and `user_roles` is the source of truth. (2) `api/trello-card.ts:513`
and `api/notify.ts` still resolve office staff from `user_metadata.role`. Those
pick notification recipients, not access, so it is a correctness wart rather than
a hole: a self-promoted user would receive lead pings. Worth moving to
`user_roles` for consistency. (3) Nothing else writes `user_roles`; account
creation is the only path and it now does.
