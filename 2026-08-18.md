# 2026-08-18

## DEPLOYED 261b735: mobile showed a partial database, four independent causes

Live: `v1.7.6.0+261b735.1787069904957`, builtAt 2026-08-18T16:18:24.957Z.
`/api/users` and `/api/contractor-jobs` both return a real JSON 401, so the
serverless functions built (version.json matching is not proof, see
[[gotcha_vercel_hobby_function_cap]]).

### Report

"My mobile instances are not showing the correct database. Missing contractor
jobs and clients." Desktop fine, same login.

### The server was never wrong

Checked live before touching anything: 328 `customer:*`, 190 `job:*`, 146
`contractor_job:*`, all present. Tombstone overlap was 1 customer and 17 cjobs,
nowhere near the reported loss. `deleted_customer_ids` holds 921 ids against 328
live rows, which looks alarming and is not the bug. PostgREST's 1000-row cap was
not being hit either (679 rows total). Role filtering ruled out.

RULE, again: **measure blast radius against live data before scoping a fix.**
Two of the four theories I would have chased on the code alone were dead.

### Cause 1, the dominant one: the pull never refreshed an expired token

`getActiveSession()` (syncEngine.ts:38) retries with `refreshSession()` before
declaring a session dead. Its own comment states the reason: Supabase's
background auto-refresh *"can miss on mobile (Safari/PWA suspended in the
field), leaving getSession() null while the refresh token is still valid."*

It was called at lines 675 and 850. **Both are push paths.** `pullFromSupabase`
called the raw `supabase.auth.getSession()` and did `if (!session) return null`
on the next line. The mobile fix was written, documented, and applied to writes
only. Reads were never ported.

A suspended phone resumes with a stale access token (the refresh timer never
fired while suspended) and silently no-ops on **every** pull trigger: mount,
focus, online, the 5-minute poll. Pushes keep working, so the device looks
connected and simply never reads. That is what made this permanent across
reloads rather than a bad first load.

**Pattern worth stealing: when you fix a bug in one direction of a bidirectional
sync, grep for the other direction the same day.** A helper whose docstring
names a specific failure mode is a strong signal that every caller of the raw
primitive it wraps is a latent instance of that same bug.

### Cause 2: the 8s boot race threw away its own result

App.tsx raced `syncFromDB()` against `SYNC_TIMEOUT_MS = 8000`. `Promise.race`
does not cancel the request, it stops awaiting it. The `.then()` holding
`setData(merged)` was **inside** the race, so on timeout the pull landed a few
seconds later, wrote correct data to IDB, and was never adopted. React kept
rendering the near-empty pre-pull state until a reload, which re-ran the same
race.

Mobile hit this far more often because an evicted IDB makes `hydrateData()`
return null, which calls `resetSyncCursor()` (dataStore.ts:376) and turns the
cheap incremental pull into a full **~912KB** reconcile (375KB customers +
410KB jobs + 133KB KV) over cellular.

Fix: adoption hangs off the pull, the timeout only releases the spinner.

**RULE: `Promise.race` for a timeout is a UI affordance, never a cancellation.**
If the losing branch has a side effect worth keeping, it must not live inside
the race.

### Cause 3: pullPrefix was unpaginated

`.like('key', prefix%)` with no `.range()`. PostgREST truncates at its max-rows
cap **with `error === null`**, so an over-cap pull is indistinguishable from a
short one. Not currently over the cap, but the failure is silent and the row
count only grows. Now walks pages of 200 ordered by key, and keeps the pages
already fetched when a later one errors: the merge is additive, so a partial
reconcile beats returning `[]`.

### Cause 4: the contractor blobs, last big values on plain localStorage

`solarflow_contractor_jobs` (86KB), `solarflow_contractors`,
`solarflow_service_rates` were still on the exact tier `stateStore` moved
AppState off for the exact stated reason, *"a data-heavy device (a contractor's
phone)"*. Two paths to an empty job list:

1. `localStorage.setItem` throws QuotaExceededError in the KV pull. The catch at
   syncEngine.ts:1204 logged and skipped the `changedKVKeys.push` **below** it,
   so no `solarflow-remote-update` fired, so `useSyncEngine` never re-read. The
   pull reported success with the list still empty.
2. iOS ITP evicts localStorage after ~7 days idle. `loadContractorJobs()` finds
   nothing and returns `demoContractorJobs`, which is `[]`. Reads as "you have
   no work" on a phone whose server holds 146 jobs.

Fix: a KV mirror in `stateStore.ts` (in-memory map for the synchronous read path
+ IndexedDB for durability). Writes land in mirror and IDB **before**
localStorage is attempted, so a quota throw is a lost cache entry instead of a
lost update. `loadContractorJobs()` stays synchronous (six sync callers, making
it async is a wide refactor) by falling back to the mirror only when
localStorage has nothing.

`hydrateKVMirror` runs in its own effect in App, not in main.tsx before render:
a private-mode IDB open can hang, and blocking first paint for every user to
rescue an evicted device is a bad trade. Guarded by `skipContractorPersist` and
only fills empty state, so it cannot clobber a list that already loaded.

Also found and fixed in passing: `saveContractors` and `saveServiceRates` had
`dbSet` **inside** the try after `setItem`, so a quota throw skipped the cloud
write entirely. That is the identical bug whose fix in `saveContractorJobs` is
documented in a comment directly above them. A fix applied to one of three
sibling functions.

### Visibility

The silent `console.warn` is replaced by a non-dismissible "Showing partial
data" banner with a Retry wired to the existing `deepSync()`. It clears itself
the moment any pull succeeds. This class of failure was invisible to users and
to us, which is why it ran long enough to be reported as "the database is
wrong".
