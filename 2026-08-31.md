# 2026-08-31

## 07fef69 - Internal messenger (staff DMs + mentions inbox)

**What shipped**

A new **Messages** view in the staff nav: an internal messenger for staff-to-staff
direct messages, with the existing @mentions inbox pinned into the same
From -> To rail.

- New `public.messages` table (migration `create_messages_table`):
  `id, from_user, to_user, body, read, created_at`, FKs to `auth.users`,
  indexes on `(from_user, to_user, created_at desc)` and `(to_user, read)`.
- RLS: SELECT if you are the sender or the recipient, INSERT only as yourself,
  UPDATE (the `read` flag) only as the recipient. **No DELETE policy**, so
  messages are not client-deletable.
- Added to the `supabase_realtime` publication. Delivery is a per-user
  `postgres_changes` INSERT subscription filtered on `to_user`, copying the
  `lib/notifications.ts` pattern exactly.

**Files**

- `solarflow-dashboard/src/lib/messenger.ts` (new) - fetch / send /
  markThreadRead / subscribe.
- `solarflow-dashboard/src/components/Messenger.tsx` (new) - left rail is the
  From -> To list (one row per staff teammate with unread count, plus a pinned
  Mentions row fed by `mentionsStore`), right pane is the thread + composer.
  Enter sends, Shift+Enter newlines.
- `solarflow-dashboard/src/components/Layout.tsx` - `Messages` nav item,
  all staff roles + sales.
- `solarflow-dashboard/src/App.tsx` - lazy import + `case 'messages'`.
- `solarflow-dashboard/scripts/ui-screens.manifest.json` - new `messages` screen.

**Two bugs found by verifying against the running app, not the diff**

1. `data.currentUser` is `null` for the first renders after a reload, which
   crashed the whole component on `currentUser.id`. Every hook now reads through
   a `uid = currentUser?.id ?? ''` and the panel renders a loading state while
   null. TypeScript did **not** catch this: the prop was typed `User` and
   `data.currentUser` is `User | null`, and the build passed anyway.
2. `data.users` still holds seeded demo rows with non-UUID ids
   (`user-mia-lopez`) until `/api/users` lands. Messaging one returned
   `400 invalid input syntax for type uuid`. The rail now filters to real auth
   UUIDs via `isAuthUser()`.

**Patterns worth reusing**

- **RLS is verifiable from the browser with a real user JWT.** Grab the
  `access_token` out of localStorage inside `page.evaluate`, capture the
  `apikey` header off any Supabase request the app already made, then hit
  PostgREST directly. Confirmed: insert `201`, select `200`, insert spoofing
  another `from_user` -> **403**, client DELETE -> silent no-op. That last one is
  the `app_data` tombstone trap again: **no DELETE policy returns HTTP 200 with
  zero rows affected**, so the delete "succeeding" proves nothing. Verified by
  SQL that the row survived.
- **`vite dev` runs no Vercel functions, so `/api/users` returns index.html and
  `data.users` never leaves its seed state locally.** A feature whose UI is
  driven by the staff directory looks empty locally and correct in production.
  Do not chase that as a bug; verify it against prod.
- **A green build is not a null-safety gate here.** See bug 1.

**Follow-ups**

- **Open question for the user:** "mentions in there (using From - To)" was read

## fbee0ad + f9b5148 - the mentions inbox never showed anyone their mentions

**The bug**

`mentionsStore` was a localStorage array. The only writer was
`fireMentionNotifications` in `MentionTextarea.tsx`, which runs in the
**notifier's** browser and stored the record under the **recipient's** user id.
Different person, different machine, different localStorage. The mentioned
person never had the row on their own device.

So `getMentionsFor(myUserId)` matched nothing except in the one case where the
notifier and the recipient were the same browser. The widget had been rendering
"No mentions yet" while **758 real mention rows, 472 of them unread, going back
to 2026-05-26**, sat in Supabase the whole time.

Found by building the messenger on top of it and noticing the pinned Mentions
row was empty for an account that plainly had mentions.

**The fix**

The server row was always the source of truth. `/api/notify` writes one
`notifications` row per mentioned user, and `App.tsx` already fetches, polls
(5 min), realtime-subscribes and read-marks that table. So `mentionsStore` is
now a **pure derivation** over `AppNotification[]`: no storage, no cache, no
event bus. Cross-device falls out for free because the table was always shared.

- `lib/mentionsStore.ts` - `getMentionsFor(notifications, userId)` and
  `unreadCountFor(notifications, userId)`. Unpicks the notifier from `title`
  and the label/body from `message`.
- `MentionsWidget` and `Messenger` take `notifications` plus read-mark
  callbacks as props. Threaded through `DispatchDashboard` -> `WidgetSlot`.
- Deleted the local write in `fireMentionNotifications`. Nobody ever read it.
- New `markAllMentionsReadRemote()` scoped `.eq('type','mention')`. The existing
  `markAllNotificationsReadRemote` clears **every** type, so wiring the mentions
  "Mark all read" to it would have silently cleared the rest of the bell.
- f9b5148: raised the notification fetch cap 50 -> 200. The inbox derives from
  the same list, so at 50 it truncates as soon as other types crowd it out, and
  one live user already had 35 mentions inside the newest 50.

**Patterns worth reusing**

- **RULE: a per-user inbox written by the OTHER user's client is always empty.**
  The write and the read ran in different browsers. Nothing errored, nothing
  logged, the list was just permanently empty, which reads exactly like "no one
  has mentioned you." **When a local write is keyed by someone else's id, it is
  already a bug.**
- **Before writing a parser for machine-composed strings, run it over every live
  row.** `regexp_match` in SQL against all 758: 0 title failures, 0 message
  failures, 0 labels spanning a newline, max label 45 chars, 0 empty bodies.
  That is what made a lazy-vs-greedy regex safe to ship, not the unit test.
  Real labels contain commas ("Jonathan Snell, SO-2608-61799") and real bodies
  are multi-line and contain their own quotes and colons.
- **An empty list is not evidence of an empty dataset.** Count the rows server
  side first. `select count(*) ... where type='mention'` would have exposed this
  in three months of it being broken.

**Verification**

- `npm run build` clean, `vitest` 615 pass / 0 fail (7 new).
- Live `version.json` = `v1.7.6.2+f9b5148.1788190794954`.
- Driven on production with a real login: the Mentions inbox renders **35 real
  mentions** with correct notifier, source label and body, unread badge 32,
  where it previously said "No mentions yet". No console errors.
- New test `src/__tests__/mentionsFromNotifications.test.ts` pins the tricky
  cases: a body containing its own quotes and colons, multi-line bodies, the
  no-body form, and an unknown shape falling back to the raw message rather
  than dropping the mention.

**Follow-ups**

- **The Ops Center `MentionsWidget` was NOT verified in place**: that widget is
  not in the test account's Ops Center layout (the grid is user-configurable and
  stored per-device), so it never rendered during the check. It shares the exact
  code path that was verified in the Messenger, but someone with the widget on
  their dashboard should eyeball it.
- `markAllNotificationsReadRemote` (the bell's "mark all") still clears every
  type including mentions. That is pre-existing and probably intended, but it
  means the bell can silently empty the mentions inbox.
- The 200 cap is still a cap. If a heavy user passes 200 notifications the inbox
  truncates again. Paginate, or query mentions separately, if that shows up.
