## d61f477 - Customers: a hidden-column filter was silently deleting rows

**Report:** "US-15643 client not showing online. Same with other customers. I can see it on the mobile view."

**First move was to check live data, not the code.** `customer:cust-se-3436011` (Jose Calderon, clientId `US-15643`) is present in Supabase, not tombstoned, not archived. So this was never a data problem, which reframed the whole thing: a record that exists on the server but is absent on one screen and present on another is a *render* problem, and the phone-vs-desktop split names the variable.

**Root cause.** `solarflow-dashboard/src/components/Customers.tsx` has exactly ONE customer list (`pagedCustomers`, line ~902). There is no separate mobile card view; `isMobile` is declared in the props interface at line 225 and never read. So mobile and desktop run identical render code over identical props. The only thing that can differ between the user's phone and their desktop is `localStorage`, and this view persists `filterType`, `powerCareOnly`, `hiddenCols` and `colFilters` under `solarops_customers_view` (line ~328).

The amplifier, and the actual bug: `matchesCols` iterated `Object.entries(colFilters)`, every saved filter, while the filter inputs only render for `visibleCols`. Type a filter into a column, then hide that column in the column picker, and the filter keeps deleting rows forever with no input on screen to explain why, across every future session on that browser.

**Fix (2 edits, ~5 lines):**
- `matchesCols` now iterates `visibleCols` and looks up `colFilters[col]`, so a hidden column's filter is inert.
- `activeFilterCount` counts only visible columns, so the clear-X reflects what the user can actually see.

**Immediate unblock given to the user (no deploy needed):**
`localStorage.removeItem('solarops_customers_view'); location.reload();`

### Patterns worth reusing

- **RULE: a record that is present in the database but missing on one client is a render bug, and the device that differs names the variable.** Confirming the row exists in Supabase took one query and eliminated the entire sync/tombstone/LWW branch of the search tree.
- **RULE: "works on mobile" is not a responsive-design clue until you confirm a mobile render path exists.** Here it did not. `isMobile` was a prop the component never read, so the phone/desktop difference could only be per-browser storage. Grep for the branch before theorising about one.
- **RULE: persisted UI state is per-browser state, and per-browser state diverges silently and permanently.** Anything saved to `localStorage` that can REMOVE rows needs its control visible whenever it is active. This is the same family as the Billing search bug (08-xx) and the Billing/RMA list-vs-kanban splits: a filter the user cannot see is a filter the user cannot undo.
- **RULE: when a filter set is keyed by column, iterate the VISIBLE columns and look up the filter, never iterate the saved filters.** Iterating the saved set lets state outlive its own UI. The header line `{sortedCustomers.length} of {customers.length} customers` was already the tell, N < M means filtered, M short means stale cache.
