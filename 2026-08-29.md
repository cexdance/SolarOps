## fcfe6f1 - Converting a lead assigns the client number and opens a $120 Site Transfer

**What changed.** `handleConvertLead` in `solarflow-dashboard/src/components/Jobs.tsx` already
claimed the `US-1XXXX` number in the Conexsol client registry sheet (shipped 08-28, e951907) and
stored it on `job.clientId`, but the SO header reads `solarEdgeClientId`, so a freshly converted
lead showed no client code. On top of stamping both fields, the conversion now sets the job up as
the work we actually do first for a new client:

- `serviceCode: 'SITE-TRX'`, `serviceType: 'Site Transfer'`
- `quoteAmount: 120`
- a flat-fee line item, `Site Transfer, SolarEdge ownership transfer (admin agentic workflow)`,
  qty 1 at $120, deduped by description so re-picking the service in the panel dropdown (which
  adds the same line, `ServiceOrderPanel.tsx:2165`) does not double it.

**Why $120 is hardcoded.** It is the `clientRateStandard` on service rate `sr-20` in
`contractorStore.ts`, and the panel already hardcodes the same number and wording. Duplicated a
second time rather than pulling the catalog into the conversion path. A third caller is the cue to
extract a shared constant.

**Files:** `solarflow-dashboard/src/components/Jobs.tsx` (import of `WOLineItem` added).

**Verified:** `pnpm build` clean, `pnpm test` 608/608, live `version.json` sha `fcfe6f1`
(`v1.7.6.2+fcfe6f1.1788007289174`), `/api/users` returns 401 (functions built, not a NOT_FOUND).

**Pattern worth reusing.** Two fields carry the client number and only one of them renders.
`clientId` is the record's own field; `solarEdgeClientId` is what the SO header prints. Writing
one and not the other looks exactly like "the registry claim failed". When a value has a storage
field and a display field, write both at the same site.
