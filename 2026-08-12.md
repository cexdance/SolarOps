# 2026-08-12

## INCIDENT: every /api/* route 404'd for ~21h, including Trello import — root cause + fix

User report: "Trello API error 404: The page could not be found NOT_FOUND iad1::s5wg5-...". That error format (`NOT_FOUND` + `iad1::` ray id, plain-text body) is Vercel's own routing 404 page, not Trello's — meaning the request never reached `api/trello-card.ts` at all.

### Diagnosis
- Confirmed every `/api/*` route 404'd identically (`solaredge`, `users`, `send-quote`, `contractor-jobs`, `notify`, `approve-quote`, `push-subscribe`, `ups-tracking`, `parse-lead-image`, `trello-card`), not a Trello-specific bug.
- Pulled the live production deployment's build logs (`vercel inspect <dpl-id> --logs`): the Vite frontend build ran fine, but **there was no serverless-functions build step at all** — no "Using TypeScript" lines (normally one per `api/*.ts` file), nothing.
- The install/build commands actually executed (`npx --yes pnpm@9.15.4 install --no-frozen-lockfile`, no `npm install &&` prefix; `npx --yes pnpm@9.15.4 run build`, no `cd solarflow-dashboard &&` prefix) matched `solarflow-dashboard/vercel.json` **verbatim**, not the repo-root `vercel.json` (which prefixes both with `cd solarflow-dashboard &&`). The live response's CSP also carried `login.xero.com`/`api.xero.com`, which only `solarflow-dashboard/vercel.json` declares.
- `vercel project inspect` reported Root Directory = `.` (correct) — but that reflects *current* settings, not what was active when the broken deployment (21h old) was actually built. The evidence is unambiguous either way: that deployment used `solarflow-dashboard/vercel.json`.
- Root cause: `solarflow-dashboard/vercel.json` was a leftover from an abandoned migration (see `FLIP_TO_DASH_RUNBOOK.md`, prepared on a `chore/flip-ready-dash` branch, never cut over per CLAUDE.md's own note). Its `solarflow-dashboard/api/` counterpart was already deleted, but the `vercel.json` file itself was never cleaned up. `vercel --prod` uses whatever `vercel.json` is in the CWD it's invoked from, **regardless of the dashboard's Root Directory setting**. Both this project's own `CLAUDE.md` and `.claude/skills/deploy/SKILL.md` (gitignored, session-editable) instructed `cd solarflow-dashboard && vercel --prod` as the manual-redeploy fallback — so anyone following that documented instruction to force a deploy would silently produce a build with **zero serverless functions**, breaking every API route for the whole team until caught.

### Fix
1. **Immediate**: redeployed correctly with `vercel --prod --yes` from the repo root (not `solarflow-dashboard/`). Verified via build log (10x "Using TypeScript", one per function) and live response (all `/api/*` routes reach the actual function: 400/401 app responses, not Vercel `NOT_FOUND`).
2. **Root cause removed** (ce5f6a1): deleted `solarflow-dashboard/vercel.json` entirely, it had no legitimate remaining purpose (its `api/` sibling is gone) and was pure landmine.
3. **Docs corrected**: `CLAUDE.md` and `.claude/skills/deploy/SKILL.md` both updated — the manual-redeploy instruction now explicitly says `cd /Users/cex/SolarOps÷ && vercel --prod --yes`, warns never to run from inside `solarflow-dashboard/`, and adds a post-deploy spot-check: hit a real `/api/*` route and confirm it's not a Vercel `NOT_FOUND` page (matching `version.json`'s sha alone is not proof the functions actually built, a gap the existing `/deploy` skill didn't cover).
4. Pushed ce5f6a1 to `main`; the normal GitHub-integration auto-deploy also verified healthy (build sha `ce5f6a1` live, all three sampled `/api/*` routes reachable).

### Why this stayed hidden for ~21h
The frontend deployed fine (Vite build succeeds identically from either `vercel.json`), so the app *looked* live and version.json matched expectations. Nothing in the existing `/deploy` skill checked that the API layer itself was reachable, only that the static build's sha matched. The user's Trello import attempt was the first thing to actually exercise an `/api/*` route since the bad deploy landed.
