## Fixes: Trello attachment mirroring, CRM file uploads, legacy blobs

Uncommitted. The working tree already held a large set of unrelated modifications from another session, so nothing was staged or pushed. Build green, 714 tests pass.

### 1. Trello import now copies attachments into our bucket

`api/trello-card.ts`, new `GET ?attachment=<trello url>&customerId=<id>` branch on the existing function (Hobby caps `api/` at 12, so no new file). Downloads the attachment with the org's Trello OAuth header, uploads it to `customer-files` with the service role, returns the public URL.

Why server-side: the download needs Trello credentials that only exist on the server, and returning bytes through the function would hit Vercel's ~4.5MB response cap. Server to Supabase has no such limit.

Guards that are load-bearing, not decoration:
- Host allowlist on the caller-supplied URL. This endpoint fetches an arbitrary URL with org credentials attached, so without it it is an SSRF hole.
- `text/html` response rejected. Trello answers an unauthorized download with a 200 HTML login page, and storing that would swap the file for a web page.
- 10MB cap matching the bucket's own `file_size_limit`, and an empty-body check.

`lib/trelloImporter.ts`, `buildImportFiles` is now async, takes a `customerId`, and returns `{ files, failed }`. **An attachment that cannot be copied is dropped and reported, never stored as a trello.com URL.** Both call sites in `Customers.tsx` surface the failures.

**RULE: an attachment stored as a third-party URL is only as shareable as that third party's auth.** The old code's comment asserted Trello URLs were "publicly accessible". They are not, and nobody checked for months because the person who imported them could always see them.

### 2. Backfill script, written but NOT yet run

`solarflow-dashboard/scripts/backfill-trello-attachments.mjs`. Dry run by default, `--apply` to write, `--limit N` to test on a few. Idempotent: skips anything already on Supabase Storage, so a re-run after a partial failure picks up only what is left.

It needs `SUPABASE_SERVICE_ROLE_KEY` in env, which is not in `.env.local`. **The 189 files are still Trello-hosted and still invisible to everyone but the importer until this is run.**

```
cd solarflow-dashboard
node scripts/backfill-trello-attachments.mjs            # dry run
node scripts/backfill-trello-attachments.mjs --apply
```

It writes back only the `files` array via PATCH, never a whole-record PUT: the script holds a snapshot read minutes earlier and customers sync whole-record LWW, so re-sending every field would revert whatever was edited in the browser meanwhile. It also checks the affected-row count rather than trusting a 200, because RLS returns success with zero rows affected.

### 3. CRM customer card no longer eats files

`components/CustomerManagement.tsx` (`customers2`, which is the **sales role's only client screen**) base64'd every dropped file into `localStorage` as a `dataUrl`. Two bugs in one: localStorage caps at a few MB and `saveCustomers` only `console.error`s the QuotaExceededError, so a dropped file could vanish with no message; and a dataUrl in one browser is unreadable by anyone else.

Both the drop handler and the paste-into-interaction path now upload through `uploadCustomerFilesPartial` and store a bucket URL. Failures raise a toast instead of disappearing. `CRMAttachment.dataUrl` is kept optional and still rendered (`att.url ?? att.dataUrl`) so attachments already sitting in someone's localStorage keep working.

**Still open, deliberately not built:** the whole `customerStore.ts` (`solarflow_customers`) is unsynced legacy, absent from `KV_SYNC_KEYS`, and seeded empty since SEC-12. The bytes are now durable and shareable, but the customer record holding the link still lives only in one browser. Making that store multi-writer needs a `KV_MERGERS` union entry, and the real question is whether sales should be on `Customers.tsx` instead. That is a product decision, not a patch.

### 4. Legacy Phase 1 blobs deleted

`app_data` keys `customers` (264 entries, frozen 2026-06-11, 166 kB) and `jobs` (22 entries, frozen 2026-05-26, 32 kB) had no reader and no writer anywhere in the codebase, while disagreeing with the per-record rows they shadowed. Archived to `_bak_legacy_blobs_20260907` and deleted.

The `syncEngine.ts` header comment claiming blob rows "are still written as a fallback" was false and is corrected. **RULE: a second source of truth for the same records is how the "which one is right" questions start.**

## Sales moved to the Customers screen, and the commits

Sales no longer have their own "Clients" view. The `customers2` route and its nav item are gone; `customers` now includes `sales` in its roles, and the App guard allowlist is `['crm', 'customers']`. The `CustomerManagement` lazy import and route case were removed, and the component file is left on disk unreferenced.

**Deletion is now gated.** `Customers.tsx` had no permit check on any of its three delete controls (bulk delete, the duplicates panel, the edit modal), because until now only admin, coo, technician and support could reach that screen. Routing sales there without a gate would have quietly handed sales bulk customer deletion. All three now check `hasPermit(currentUser, 'customers.delete')`, which admin holds and sales does not. Money was already covered by `formatMoney` and the SHOW_MONEY policy.

**RULE: widening who can reach a screen is a permissions change, not a routing change.** Re-read what the screen lets you do before you add a role to it.
