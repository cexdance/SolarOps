## Deep dive: Miriam Cabrera imported wrong (9e3a1e6)

### Defect 1: nothing ever maintained `pipelineStage` after create

The webhook stamped `pipelineStage:'leads'` at import and never touched it again. `matchTargetList` only recognises a move **INTO** the leads list; every other move (`updateCard` with a different `listAfter`) fell through to the backfill path, which did not touch the stage.

Measured against live data: **32 of 56 cards were in the wrong LL column.**

| drift | count |
|---|---|
| `leads` -> `email_follow_up` | 16 |
| `leads` -> `done` | 5 |
| `leads` -> `site_transfer_processing` | 2 |
| `leads` -> `closed_archived` | 1 |
| `needs_scheduling` -> `closed_won` | 2 |
| `work_done_collect` -> `closed_won` | 2 |
| 4 other one-offs | 4 |

So the LL "Leads" column was showing 40 cards when only ~16 were still leads. **The funnel was lying about the state of the business.**

Fix: the stage is reconciled from the card's **current** `idList`, read on **every** event (not just list moves). That makes it self-healing: a missed webhook delivery, or a move made while a deploy was in flight, is corrected by the next event of any kind on that card.

### Defect 2: the list->stage map must be keyed by ID, never by index

The board's list order and `PIPELINE_STAGES` **do not agree**:

```
Trello  [7] Work Done - Collect Payment      PIPELINE_STAGES[7] needs_follow_up
Trello  [8] Needs follow-Up Service          PIPELINE_STAGES[8] work_done_collect
```

The 2026-08-10 bulk import mapped them positionally, which silently swaps those two columns. `LIST_STAGES` is now keyed by list id, and an unknown list yields `undefined` so the stage is left alone rather than the card being dumped into a wrong column. Pinned in the self-check, since this is invisible on inspection.

**RULE: never map two ordered lists onto each other by index across a system boundary.** The other side can reorder at any time, and it fails silently rather than loudly.

### Defect 3: notes kept the create-time placeholder

Trello writes the card description a beat *after* `createCard` fires, so a card imported inside that window kept `Auto-imported from Trello card "image.jpeg"` forever, losing the real lead text, the contact block, the Contract Name and the HS_ID. `backfillLeadJob` repaired name/leadInfo/labels but never notes. **32 cards affected.** Now repaired, but only when the note still matches that exact placeholder shape, so a note the team wrote is never clobbered.

## Authority decision: the app owns the record, Trello is intake only (17b6097)

User: "Apps win Trello for now will be the intake of the lead."

So Trello is where a lead arrives, nothing more. Once the card is on the LL board the office works it in the app, and nothing arriving from Trello may overwrite what the app holds.

| field | rule |
|---|---|
| `pipelineStage` | **NEVER** touched after create. The app owns the column. |
| `labels` | union-**ADD** only, and only while the card is still at `INTAKE_STAGE` ('leads'). Never removes, never reorders. |
| name / `leadInfo` / notes | fill **only where the job's value is empty or still the create-time placeholder**. |

The reasoning for the split: completing an import that Trello delivered incomplete is not an override. `createCard` fires before the description is written and the attachment uploaded (+1s typically, +82min when a human drops the screenshot later), so the follow-up events are finishing the original intake, not making a new decision. A label added seconds after the card is created is part of that same intake, which is why labels union-add during the intake stage but stop contributing the moment the lead is being worked.

This supersedes the stage mirroring added in `9e3a1e6` earlier the same day. That was correct while Trello was the system of record, and the one-time reconciliation it performed still stands (55/55 columns matched Trello at that moment). From here the app is authoritative. `stageForList` survives for the create path alone (which intake list a new lead arrived in), and keeps its by-id-not-by-index self-check assertions.

## Deleting a Trello card now removes the lead (9076903)

User deleted the "Get started with Email for Trello" card in Trello; it was still on the LL board. The webhook had **no deleteCard path at all**, so a deleted card left its lead behind forever. Three were stranded: both "Email for Trello" onboarding cards and one duplicate Pedro Cordon.

### How it works
`deleteCard` reaps the lead: the job id goes into the shared `deleted_job_ids` tombstone row (which every client union-merges into localStorage on pull, `syncEngine.ts`) and the per-record `job:` row is removed, so the lead disappears on every device rather than being re-pulled forever.

- **Tombstone is written BEFORE the row delete.** Reversed, a client still holding the job locally would push it straight back.
- **The delete uses the service role**, so it is not subject to the `app_data` RLS that makes the client-side reap a silent no-op. Verified: the rows are physically gone, not just tombstoned.

### What it refuses to delete
`canReapLead()` only allows a reap while the lead is **untouched intake**: still on the leads column, no `customerId`, no `woNumber`, no logged activity. Trello is where a lead ARRIVES; someone tidying up Trello must never be able to delete real work. A worked lead is kept and shouted about in the log.

**Archived (closed) cards are deliberately NOT reaped.** Archiving is reversible in Trello; a tombstone is not.

### The guard, and why it is not boardDecision()
`boardDecision()` reads the `idBoard` Trello returns for a card, which is unforgeable, but that is useless here because the card no longer exists. Instead the handler **confirms with Trello that the card really 404s** before reaping. That is the one claim an attacker cannot forge: they cannot make a live card 404. The card id is also shape-checked (24 hex) before it reaches a URL.

Verified live against production:

| probe | result |
|---|---|
| deleteCard for a card that still exists (Miriam) | `skipped: card still exists in Trello`, record untouched |
| deleteCard with `../../etc/passwd` | `400 Malformed card id` |
| deleteCard for a well-formed id that never existed | `result: absent`, no row, harmless |

### Reaped
`scripts/backfill-ll-trello-cards.mjs --reap` finds leads whose card is already gone and replays this same deleteCard path, so the rules live in one place. Ran it: 3 reaped, tombstones 29 -> 32, LL Trello cards 58 -> 55.

## "Log a contact action" was losing the typed note (f3c7641) + contact trifecta (e27d69d)

User: "Log a contact Action is not saving the note. lost the last text on this card."

### What was saved
Both entries on Shoshana kramer's lead read exactly `"Call: contacted"`. That string is the **empty-text fallback** in `log()`, so the textarea was empty at click time and the typed note never reached the handler. The binding itself (`value={logText} onChange=...`) was correct.

### What actually wiped it
The `change_log` for that lead shows the shape:

```
14:06:52, :55, :56   job.update   <- contact-field onBlur saves
14:07:48.028         job.update   <- "Log Call" #1, empty note
14:12:08.715         job.update   <- another onBlur save
14:12:18.711         job.update   <- "Log Call" #2, empty note, 10s later
```

Every contact field saves on **blur**, and that save runs `onUpdateJob -> saveData -> sync` asynchronously, so the resulting re-render lands *while the user is already typing the note*. Two things then destroyed the text:

1. **The parent unmounted the panel on a transient lookup miss.** `Jobs.tsx` did `const lead = jobs.find(...); if (!lead) return null;`. `jobs` is replaced wholesale by every sync pull/hydrate, so any momentary miss dropped the panel and every piece of unsaved state in it.
2. `logText` lived in `useState`, so any remount from any cause reset it to `''`.

**What made it invisible: the silent fallback.** A lost note still produced a plausible `"Call: contacted"` entry, so the UI looked like it worked.

### Fix
- `Jobs.tsx` keeps the last resolved lead in a ref and renders that instead of unmounting on a transient miss.
- `LeadPanel` holds the draft note in a **module-scope map keyed by job id**, so it outlives a remount from any cause, not just the two found here. Cleared once the entry is logged. 4 tests pin the contract.

**RULE: a component holding unsaved user input must not depend on staying mounted.** Anything looked up out of a synced array can vanish for a frame, and `useState` has no memory across that.

### e2cd8ad - per-field LWW for jobs

Phase 2 of `spec_job_field_level_merge`, closing out `gotcha_whole_record_lww_clobber`. Phase 1 (`6749ce2`, 06-30) had been stamping `Job.fieldTimes` on every write for ~8 weeks against the 1-2 the spec scoped.

Grounded before touching it (the "count live records before building on a timestamp field" rule): **142 of 202 live `job:%` rows carry `fieldTimes`, 118 with maps of >3 keys.** The other 60 fall back to record `updatedAt`, which reduces exactly to the old behavior, so there is no regression path for them.

`mergeJobPair` retired, replaced by `mergeJobFields(a, b)` in `lib/syncEngine.ts`. Each field resolves against `fieldTimes[field]` via a `fieldTime()` helper that falls back to `recordTime()`. Order-independent, so the jobs loop in `mergeRemote` dropped its `remoteWins()` call.

**Two things the spec did not have, both found by grepping the other direction of the sync:**

1. The Realtime handler at `hooks/useSyncEngine.ts:155` called `mergeJobPair(job, j)` with **no `remoteWins()` check at all**. The pull path checked; this one handed the incoming remote copy an unconditional win over every scalar, even against a newer local edit. That made Realtime strictly worse than pull. The order-independent merge fixes it for free.
2. `deletedPhotoStems` is a **tombstone list** and was being resolved by LWW. A stale side could shrink it and let a deleted photo get re-imported from `cj.photos`, which has no delete tombstones of its own. Union-only now, alongside the append-only feeds.

Field classes in the merge: `APPEND_FIELDS` (activityHistory, auditLog) unioned by id, `TOMBSTONE_FIELDS` (deletedPhotoStems) union-only, `woPhotos` keeps its deletion-aware merge but the authoritative side is whoever touched `woPhotos` last rather than whoever wrote the record last, everything else per-field LWW.

The `c0da61e` ServiceOrderPanel band-aid was deliberately **left in place**. The spec called removing it optional; it also covers a panel-remount case the merge does not, so removing it is a separate decision with its own risk.

## Item 5: app_data contractor row isolation (the real P0)

Commit `8da0d9e` (client) + migration `app_data_contractor_row_isolation` (database).

### What was wrong

`app_data` had RLS **enabled**, which looks correct on a dashboard, but all three policies were bare `auth.role() = 'authenticated'` with no per-user or per-role predicate. Any logged-in session, contractor included, could read and write all 697 rows: 330 customers, 202 jobs, the CRM lead blob, the contractor roster, service-rate pricing. The contractor boundary existed only in client-side `lib/authRouting.ts`, so a contractor hitting PostgREST directly with their own valid JWT walked straight around it. `change_log` has the identical gap and is NOT yet fixed.

### The discovery that changed the scope

Item 5 was scoped as a one-migration job. It was not, and the reason is the single most useful thing to come out of this session.

A "Phase 3" had already moved contractor READS off PostgREST onto `/api/contractor-jobs` (`contractorScopedPull.test.ts`). The write direction was never done. **That was not a latent gap, it was live:** `pullContractorScope()` returns the endpoint's jobs and customers WITHOUT `markClean`, and `isDirty()` treats any key with no baseline as dirty. So every record the scoped endpoint handed back was pushed straight back up as an admin `job:{id}` / `customer:{id}` row. **Contractors have been writing admin records they were not even allowed to read.**

This is exactly the rule already in memory: *fix one direction of a bidirectional sync, grep the other direction THAT DAY.*

It also made both naive RLS variants unsafe:
- Block writes only -> contractor pushes throw a policy violation, their sync stops.
- Block reads only -> `dropStaleRows` reads the server copy to decide whether a local row is stale. With reads denied it gets an EMPTY result, no error, concludes "no server copy exists", and keeps every row. **A read-only restriction would have stripped the stale-write guard and made contractor overwrites MORE dangerous, not less.**

So the halves had to move together, client first.

### What shipped

**Client (`8da0d9e`, Phase 4):** `pushToSupabase` marks all `customer:`/`job:` rows clean for a contractor session, so none are ever pushed. `markClean` rather than a filter: an unmarked row stays dirty for the life of the session and gets retried on every push. Contractor edits are unaffected, they persist to the `solarflow_contractor_jobs` KV blob via `saveContractorJobs`. Deployed and confirmed live BEFORE the database change, because the reverse order breaks contractor sync.

**Database:** all three policies now additionally require, for a contractor, that the key is neither `customer:%` nor `job:%`. Role source matches `isContractorAccount()` exactly: `user_metadata.role === 'contractor'`. Still no DELETE policy, so deletes stay blocked.

### Verification

Every case dry-run in a transaction with ROLLBACK before applying, then re-verified against the live policies:

| session | customers | jobs | total |
|---|---|---|---|
| contractor | 0 | 0 | 165 |
| admin | 330 | 202 | 697 |
| no role at all | 330 | 202 | 697 |
| dual-role staff (`support` + `isContractor`) | 330 | 202 | 697 |

Plus a NEGATIVE test: a contractor `insert` of a `job:` row raises `insufficient_privilege` (wrapped in a `DO` block that raises "POLICY HOLE" if the insert ever succeeds, so the test cannot pass vacuously).

Contractors keep all 165 rows the portal needs, including `solarflow_contractors`, `solarflow_service_rates`, `solarflow_crm_data` and the tombstone lists. Their real job data is unaffected because `/api/contractor-jobs` reads with the **service role**, which bypasses RLS entirely.

**End-to-end:** ran the snap-ui capture against PRODUCTION with a real staff login after the policy went live. 23/24 screens, and Customers rendered "329 of 329". Staff access provably intact. (Catalog changes reverted, this deploy had no UI change; the capture was used purely as a verification tool.)

## Trello webhook: the payload's board id was the only board check  (`9b53215`)

Started as "set `TRELLO_API_SECRET`", a config task. Reading the code first turned up a second, larger hole that the secret alone would not have covered.

### Confirmed, not inferred

`vercel env ls production` lists no `TRELLO_API_SECRET`. So `verifyTrelloSignature`'s `if (!secret) return true;` really is returning true unconditionally in production. Also absent: `TRELLO_API_KEY` / `TRELLO_API_TOKEN`, so the server is running on the `VITE_`-prefixed fallbacks.

### The actual hole

`matchTargetList()` reads the board id from `action.data.board.id`, which is **caller-supplied**. That was the only board check. With the signature failing open and **the repo being PUBLIC**, the real board and list ids are readable in the source file itself.

Attack: create a card on your OWN Trello board, POST a payload naming OUR board and list but YOUR card id. `fetchCardForLeadImport` fetches your card (our token reads any public card) and imports its name, description, labels and mined contact fields as a lead, firing the new-lead notification to ~13 office users.

Setting the secret would have closed this. But the secret is a user action, and the code should not have been relying on a caller-supplied board id in the first place.

### Fix

Ask Trello for the card's `idBoard` and check THAT. It comes from Trello, not from the payload, so it cannot be forged, and it holds while the signature fails open. A bogus card id never even reaches the check, the fetch throws on the 404 first.

**`boardDecision()` is deliberately three-way, not a boolean:**

| result | meaning | action |
|---|---|---|
| `allow` | idBoard is one of TARGET_LISTS' boards | proceed |
| `reject` | idBoard present and foreign | 403, the real attack |
| `unverified` | idBoard ABSENT | allow + `console.error` |

The third case is the important design call. An attacker cannot cause an absent `idBoard`: the fetch is ours, it explicitly requests the field, and every Trello card belongs to a board. Absence therefore means our query or Trello's response shape changed, i.e. a bug. **Rejecting on a bug would 403 every legitimate lead and take the whole pipeline down, which is precisely the outcome the fail-open signature branch exists to prevent.** So it is allowed through and shouted about.

**RULE: when adding a guard to a pipeline whose explicit design is fail-open, separate "the check failed" from "the check could not run." Collapsing them into a boolean converts a bug into an outage.**

Also made the fail-open path log a warning. Silence is why unset was the steady state long enough for nobody to notice.

### VITE_ prefix scare, investigated and clean

The server falls back to `VITE_TRELLO_API_KEY` / `VITE_TRELLO_TOKEN`, and Vite inlines `VITE_`-prefixed vars into the browser bundle, which would put Trello credentials in public JS.

Checked properly rather than reasoned about: crawled the live bundle, following lazy chunk imports (per the repo's own rule that a bundle check must enumerate Vite's chunks). **108 chunks, 3.08 MB, zero `VITE_TRELLO` references, zero 64-hex strings (Trello token shape), zero 32-hex strings in any chunk mentioning trello.** Clean, because Vite only inlines vars that client code actually references, and no client source reads them.

**Latent trap though:** the day anyone writes `import.meta.env.VITE_TRELLO_TOKEN` in client code, the credential ships publicly with no warning. Hygiene fix is to rename both to non-`VITE_` names in Vercel; `api/trello-card.ts` already PREFERS `TRELLO_API_KEY`/`TRELLO_API_TOKEN` and only falls back, so the rename is a drop-in.

### Testing

`trelloWebhookBoardGuard.test.ts`, 10 cases. Includes a **positive** signature case: without it, a bug making the HMAC always mismatch would pass every rejection test while silently failing the webhook CLOSED and killing the lead pipeline. Also asserts that `matchTargetList` happily accepts a forged board/list, which is the whole reason the `idBoard` check has to exist.

No forged POST was fired at production; that would exercise the real lead pipeline.

### Still needs the user

- **Set `TRELLO_API_SECRET` in Vercel.** Still worth doing: it authenticates the caller, whereas the board check only constrains what they can inject. Defence in depth, and the code now enforces the signature the moment the var exists.
- **Rename `VITE_TRELLO_API_KEY` -> `TRELLO_API_KEY` and `VITE_TRELLO_TOKEN` -> `TRELLO_API_TOKEN`** in Vercel, to remove the latent bundle-exposure trap.

## change_log read/write separation (the side door on this morning's P0)

Migration `change_log_contractor_read_isolation` + commit `9f24b45` + index `change_log_user_email_idx`.
Plan: `PLAN_change_log_rls.md`.

### Why it was not the app_data treatment

`app_data` got one predicate applied to SELECT, INSERT and UPDATE alike. `change_log` is asymmetric and that asymmetry IS the design:

- **Contractors must keep WRITING.** Every contractor-side edit calls `logJobChange`. `components/contractor/JobDetail.tsx` imports exactly `logChange, logJobChange, describeUrl`.
- **Contractors never READ.** The only Supabase read paths are staff surfaces: `ServiceOrderPanel.tsx:759` (`fetchLogForEntity`, the SO History tab) and `admin/UserActivityLog.tsx:70` (`fetchLogForUser`).

So SELECT excludes contractors and INSERT is untouched. 17,838 rows, of which **13,299 contain an email and 957 are customer records**, were readable by any contractor until now.

### Correction: the audit log was NOT forgeable the way I claimed

I said earlier that `user_email` being client-supplied made the audit log forgeable. Too strong. Migration `20260804_change_log_server_stamped_actor.sql` had already installed `change_log_stamp_actor_trg`, which stamps `actor_uid` from `auth.uid()`. **Verified live: 4,210 rows since 2026-08-05, ZERO NULL `actor_uid`.** All 13,478 NULLs predate it.

So `user_email` can lie but `actor_uid` cannot, and a mismatch between them is what makes a forgery visible. That was already designed correctly and the plan does nothing to it. No `actor_uid = auth.uid()` WITH CHECK was added, because it would be redundant with the trigger.

### Second bug found while reading (`9f24b45`)

`pushEntry` used a plain `.upsert()` with no conflict option. `change_log` has **no UPDATE policy by design** (append-only at the RLS layer), so on a redelivery the upsert took the UPDATE path and hit a policy violation. The entry HAD landed; what failed was the local "mark synced" write below it, so the same row was re-pushed on every flush forever, swallowed by the catch. Now `{ onConflict: 'id', ignoreDuplicates: true }`, i.e. ON CONFLICT DO NOTHING, which is the correct semantic for an audit row.

### Verification

Dry-run in a transaction with ROLLBACK, then re-verified against the live policies:

| session | change_log rows visible |
|---|---|
| contractor | 0 |
| admin / sales / no-role / dual-role staff | 17,838 |

Negative/positive write test: a contractor INSERT wrapped in a `DO` block that raises `REGRESSION` if denied. It was allowed, staff could see the row, and `actor_uid` was stamped as the contractor's real uid even though `user_email` said something else.

**End-to-end through the REAL PostgREST path with a REAL staff JWT** (not a SQL simulation), using the project's own `.env.local` staff account:

```

signed in as staff   -> role=admin

fetchLogForEntity    -> job=found rows=9        <- SO History tab renders
```

**Note the anonymous line: 0 rows with NO error.** That is the whole reason the checks assert row counts rather than trusting the UI.
