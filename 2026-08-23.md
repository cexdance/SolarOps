## Deep dive: Miriam Cabrera imported wrong (9e3a1e6)

User flagged `trello.com/c/J73XuuaL` (Miriam Cabrera) as "not imported correctly". It was not one bad card, it was two systemic defects affecting most of the board.

### Symptom vs reality

| | Trello | SolarOps (before) |
|---|---|---|
| List / column | **Email Marketing Follow-Up** (since 08-05) | `pipelineStage: 'leads'` |
| Notes | full lead email: name, phone, email, zip, "notes: My solar does not work", Contract Name, HS_ID | `Auto-imported from Trello card "image.jpeg"` |

Name, labels and `leadInfo` were already correct (fixed earlier today), which is exactly why the card looked *nearly* right and the real problems were easy to miss.

### Defect 1: nothing ever maintained `pipelineStage` after create

The webhook stamped `pipelineStage:'leads'` at import and never touched it again. `matchTargetList` only recognises a move **INTO** the leads list; every other move (`updateCard` with a different `listAfter`) fell through to the backfill path, which did not touch the stage.

Measured against live data: **32 of 56 cards were in the wrong LL column.**

| drift | count |
|---|---|
| `leads` -> `email_follow_up` | 16 |
| `leads` -> `done` | 5 |
| `leads` -> `site_transfer_processing` | 2 |
| `leads` -> `closed_archived` | 1 |
| `needs_scheduling` -> `closed_won` | 2 |
| `work_done_collect` -> `closed_won` | 2 |
| 4 other one-offs | 4 |

So the LL "Leads" column was showing 40 cards when only ~16 were still leads. **The funnel was lying about the state of the business.**

Fix: the stage is reconciled from the card's **current** `idList`, read on **every** event (not just list moves). That makes it self-healing: a missed webhook delivery, or a move made while a deploy was in flight, is corrected by the next event of any kind on that card.

### Defect 2: the list->stage map must be keyed by ID, never by index

The board's list order and `PIPELINE_STAGES` **do not agree**:

```
Trello  [7] Work Done - Collect Payment      PIPELINE_STAGES[7] needs_follow_up
Trello  [8] Needs follow-Up Service          PIPELINE_STAGES[8] work_done_collect
```

The 2026-08-10 bulk import mapped them positionally, which silently swaps those two columns. `LIST_STAGES` is now keyed by list id, and an unknown list yields `undefined` so the stage is left alone rather than the card being dumped into a wrong column. Pinned in the self-check, since this is invisible on inspection.

**RULE: never map two ordered lists onto each other by index across a system boundary.** The other side can reorder at any time, and it fails silently rather than loudly.

### Defect 3: notes kept the create-time placeholder

Trello writes the card description a beat *after* `createCard` fires, so a card imported inside that window kept `Auto-imported from Trello card "image.jpeg"` forever, losing the real lead text, the contact block, the Contract Name and the HS_ID. `backfillLeadJob` repaired name/leadInfo/labels but never notes. **32 cards affected.** Now repaired, but only when the note still matches that exact placeholder shape, so a note the team wrote is never clobbered.

### Verified on the reported card
After the fix, Miriam Cabrera: `pipelineStage: email_follow_up` (matches Trello), both labels, full `leadInfo`, and the complete lead email in notes including "My solar does not work" and HS_ID 59807628084.

## Authority decision: the app owns the record, Trello is intake only (17b6097)

User: "Apps win Trello for now will be the intake of the lead."

So Trello is where a lead arrives, nothing more. Once the card is on the LL board the office works it in the app, and nothing arriving from Trello may overwrite what the app holds.

| field | rule |
|---|---|
| `pipelineStage` | **NEVER** touched after create. The app owns the column. |
| `labels` | union-**ADD** only, and only while the card is still at `INTAKE_STAGE` ('leads'). Never removes, never reorders. |
| name / `leadInfo` / notes | fill **only where the job's value is empty or still the create-time placeholder**. |

The reasoning for the split: completing an import that Trello delivered incomplete is not an override. `createCard` fires before the description is written and the attachment uploaded (+1s typically, +82min when a human drops the screenshot later), so the follow-up events are finishing the original intake, not making a new decision. A label added seconds after the card is created is part of that same intake, which is why labels union-add during the intake stage but stop contributing the moment the lead is being worked.

This supersedes the stage mirroring added in `9e3a1e6` earlier the same day. That was correct while Trello was the system of record, and the one-time reconciliation it performed still stands (55/55 columns matched Trello at that moment). From here the app is authoritative. `stageForList` survives for the create path alone (which intake list a new lead arrived in), and keeps its by-id-not-by-index self-check assertions.

## v1.7.6.2 - per-field job merge (Phase 2) + Service Order panel close wiring

### e2cd8ad - per-field LWW for jobs

Phase 2 of `spec_job_field_level_merge`, closing out `gotcha_whole_record_lww_clobber`. Phase 1 (`6749ce2`, 06-30) had been stamping `Job.fieldTimes` on every write for ~8 weeks against the 1-2 the spec scoped.

Grounded before touching it (the "count live records before building on a timestamp field" rule): **142 of 202 live `job:%` rows carry `fieldTimes`, 118 with maps of >3 keys.** The other 60 fall back to record `updatedAt`, which reduces exactly to the old behavior, so there is no regression path for them.

`mergeJobPair` retired, replaced by `mergeJobFields(a, b)` in `lib/syncEngine.ts`. Each field resolves against `fieldTimes[field]` via a `fieldTime()` helper that falls back to `recordTime()`. Order-independent, so the jobs loop in `mergeRemote` dropped its `remoteWins()` call.

**Two things the spec did not have, both found by grepping the other direction of the sync:**

1. The Realtime handler at `hooks/useSyncEngine.ts:155` called `mergeJobPair(job, j)` with **no `remoteWins()` check at all**. The pull path checked; this one handed the incoming remote copy an unconditional win over every scalar, even against a newer local edit. That made Realtime strictly worse than pull. The order-independent merge fixes it for free.
2. `deletedPhotoStems` is a **tombstone list** and was being resolved by LWW. A stale side could shrink it and let a deleted photo get re-imported from `cj.photos`, which has no delete tombstones of its own. Union-only now, alongside the append-only feeds.

Field classes in the merge: `APPEND_FIELDS` (activityHistory, auditLog) unioned by id, `TOMBSTONE_FIELDS` (deletedPhotoStems) union-only, `woPhotos` keeps its deletion-aware merge but the authoritative side is whoever touched `woPhotos` last rather than whoever wrote the record last, everything else per-field LWW.

The `c0da61e` ServiceOrderPanel band-aid was deliberately **left in place**. The spec called removing it optional; it also covers a panel-remount case the merge does not, so removing it is a separate decision with its own risk.

Tests: `src/__tests__/mergeJobFields.test.ts`, 8 cases including the exact 06-30 contractor-revert scenario, the legacy-fallback reduction, tombstone union, and photo-deletion-with-in-flight-upload.

### dbc6bb8 - Service Order panel close wiring

Four files were sitting uncommitted in the tree as the **consumer half of a feature whose producer half had already shipped**. `ServiceOrderPanel.tsx:294` already declared `onSave: (job, shouldClose?) => void` and `:1458` already called `onSave(partialJob, !keepOpen)`, but all four call sites ignored the second argument, so the panel never closed on save in production. Wired up in `App.tsx`, `Customers.tsx` (create + edit), `Jobs.tsx`, `SiteProfilePanel.tsx`.

Also: a job card in the customer detail panel now opens its Service Order on click, guarded by `closest('button,a')` so the existing inline actions still work.

### Patterns worth reusing

- **Check the producer side before shipping consumer-side call sites.** A diff that only adds a parameter to callbacks is dead code unless something passes the argument. Here it was the reverse of the usual failure: the producer shipped first and the feature sat inert.
- **A spec's call-site list can be stale.** `spec_job_field_level_merge` named the `mergeRemote` loop only; `grep mergeJobPair` found a second, buggier call site in the Realtime hook. Grep for the symbol, do not trust the spec's inventory.
- **Any array inside a per-field merge still needs its class decided.** Per-field LWW is not automatically safe for arrays: append-only feeds need union, tombstone lists need union, only genuinely scalar-ish arrays can LWW.

### Follow-ups

- **Customer Realtime path has the same unconditional-remote-win bug** that jobs just lost: `useSyncEngine.ts` `onCustomer` calls `mergeCustomerPair(customer, c)` with no `remoteWins()`. Customers carry no `fieldTimes`, so the fix is record-level LWW correctness, not per-field. Task chip spawned, not fixed here.
- `lineItems` is still whole-array LWW. Per the spec, acceptable until someone reports a concurrent line-item edit.
- Client clocks still stamp `fieldTimes`, same skew exposure as before, not worse. Upgrade path if skew bites: Lamport counters. The server cannot stamp per-field because it does not know which fields changed.

## Production hardening pass 1: items 1-4 of PRODUCTION_READINESS_PLAN.md

Commits: `96abca0`, `87531ab`, `9ee60fa`. Live: `v1.7.6.2+9ee60fa`.
Plan doc: `PRODUCTION_READINESS_PLAN.md`. DB audit: `DB_RLS_AUDIT.md`.

Triggered by an outside developer calling SolarOps "a nice proof of concept, not a production app." Three specialist agents audited API auth, live DB posture, and code fragility. Every headline finding was re-verified by hand before acting; two needed correcting.

### Backup tables: LOCKED, not dropped

`_bak_crm_leads_20260808` (1 row) and `_bak_lljobs_20260809` (40 rows) had RLS disabled, so the anon key could read and modify lead PII. Migration `lock_pii_backup_tables_rls` enables RLS with ZERO policies, which denies anon and authenticated outright while `service_role` still bypasses, so the data stays recoverable. Chose lock over drop deliberately: destroying data is not reversible and was not mine to decide. Confirmed zero source references first (only markdown notes matched).

### `GET /api/trello-card` was leaking lead PII to anonymous callers  (`96abca0`)

`api/trello-card.ts` imported `requireUser` nowhere. Any anonymous caller supplying a card id got that card proxied back using the org's `TRELLO_API_KEY`/`TRELLO_API_TOKEN`: names, phones, emails, addresses from the description, checklists, custom fields and comments, plus org API quota spent per call.

Proven live BEFORE the fix: an unauthenticated GET with a bogus id returned `{"error":"Trello API 400: Bad Request"}`. The 400 came from **Trello**, not our auth layer, which is what made it conclusive.

Identical to the `solaredge.ts` bug fixed 08-03 ("returned 361 customers' names and addresses to an unauthenticated GET"). The fix was never applied to its neighbour. Guard placed AFTER the HEAD and POST branches so Trello's callback verification and the webhook stay public; only the GET proxy is gated. Server-side only, the sole client call site (`fetchTrelloCard`) already used `authedFetch`.

**GOTCHA: a CDN-cached response made the fix look incomplete.** Post-deploy, `/api/trello-card` with no params still returned the old 400 while `?cardId=...` returned 401. Same commit, contradictory answers. It was a cached response from the pre-fix probe of that exact URL. Re-probing with a cache buster showed `x-vercel-cache=MISS` and 401 on both. **RULE: always cache-bust when verifying a security fix on a GET endpoint. A cached 200 can make an unfixed endpoint look fixed, which is the dangerous direction of this mistake.**

### CI was red on EVERY commit and nobody knew  (`9ee60fa`)

Wiring the deploy gate immediately exposed why the gate mattered: CI had been failing on every run for at least a day, and it was invisible because the Vercel Git integration deployed regardless.

Cause: `apiResilience.test.ts` imports `api/trello-card.ts`, which lazily imports `web-push`. `web-push` lives in the **repo-root** `package.json` (with `@vercel/node` and `docx`) because it belongs to the serverless `api/` tree, but CI only ran `pnpm install` inside `solarflow-dashboard`. The import could not resolve and Test died at 580/581. `vercel.json`'s `installCommand` already installs BOTH trees; CI never mirrored it.

**RULE: this repo has TWO dependency trees. Any runner that touches `api/` must install the root one too. A green local run proves nothing here, because a dev machine always has root `node_modules` present.**

### Deploy is now gated on CI  (`87531ab` + `9ee60fa`)

Vercel deployed on push IN PARALLEL with CI, so a red run stopped nothing (29 of the last 30 commits were direct pushes to main). Added a `deploy` job with `needs: build-and-test`, which also polls `version.json` until the live sha matches and asserts `/api/users` returns 401 rather than a NOT_FOUND page.

The job deliberately does NOT inherit the top-level `solarflow-dashboard` working-directory, because `vercel --prod` resolves `vercel.json` from its CWD, which is the 08-12 zero-function outage.

**MY BUG, worth remembering: the `secrets` context is NOT available in a job-level `if`.** I used `secrets.VERCEL_TOKEN != ''` there for self-activation. That makes the whole workflow file invalid, so the run started **zero jobs** and reported a bare "failure" with no logs and nothing to click into. **A run with 0 jobs means the workflow never parsed; a run with 1 job that failed is a real failure. Check the job count first, it tells you which kind you have.** The guard now lives inside the step, where `secrets` is legal.
