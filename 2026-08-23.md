### 3. What was missing, now shipped (6d5ef81)

**Labels were never imported.** The webhook wrote no `labels` at all; the 21 jobs that had them came from the one-off 08-10 script. Now `toJobLabels()` maps Trello labels into the same `{name,color}` shape `LabelPicker` writes, so an imported chip is indistinguishable from a hand-added one. Colour-only labels are dropped (they would render as blank chips).

**Label changes mirror back, but ONLY on `addLabelToCard`/`removeLabelFromCard`** (`LABEL_ACTIONS`). Gating on real label events is deliberate: the team can also set labels in-app, and if every `updateCard`/`commentCard` re-pushed Trello's set, an in-app label would be silently reverted by an unrelated card edit. On a real label event Trello wins via **whole-set replace**, because a union can never express a removal.

**New-lead notification** to `admin`/`coo`/`support` (13 users; contractors excluded, sales excluded since they still cannot reach the LL board):
- a `notifications` row -> the bell, which syncs to every signed-in browser
- best-effort web push to registered devices (3 of the 13 have one)
- fires only on `jobResult === 'created'`, so a redelivery or a card dragged out and back cannot re-ping the office
- notification id derived from the card id, so a duplicate insert is ignored rather than doubled
- `AppNotification.type` gained `'new_lead'`; `NOTIF_GROUPS` + a "Leads" chip added in `4abfe7c` (without it the type showed under All/Unread but could not be filtered)

**`web-push` is imported lazily INSIDE a try/catch.** `setVapidDetails` at module scope with malformed VAPID env is exactly what took all of `/api/notify` down for two days ([[gotcha_notify_vapid_module_crash]]). Here the dynamic import and the init are both inside the guard, so a broken VAPID can only cost a log line, never the lead import.

## Deep dive: Miriam Cabrera imported wrong (9e3a1e6)

User flagged `trello.com/c/J73XuuaL` (Miriam Cabrera) as "not imported correctly". It was not one bad card, it was two systemic defects affecting most of the board.

### Symptom vs reality

| | Trello | SolarOps (before) |
|---|---|---|
| List / column | **Email Marketing Follow-Up** (since 08-05) | `pipelineStage: 'leads'` |
| Notes | full lead email: name, phone, email, zip, "notes: My solar does not work", Contract Name, HS_ID | `Auto-imported from Trello card "image.jpeg"` |

Name, labels and `leadInfo` were already correct (fixed earlier today), which is exactly why the card looked *nearly* right and the real problems were easy to miss.

### Defect 1: nothing ever maintained `pipelineStage` after create

The webhook stamped `pipelineStage:'leads'` at import and never touched it again. `matchTargetList` only recognises a move **INTO** the leads list; every other move (`updateCard` with a different `listAfter`) fell through to the backfill path, which did not touch the stage.

Measured against live data: **32 of 56 cards were in the wrong LL column.**

| drift | count |
|---|---|
| `leads` -> `email_follow_up` | 16 |
| `leads` -> `done` | 5 |
| `leads` -> `site_transfer_processing` | 2 |
| `leads` -> `closed_archived` | 1 |
| `needs_scheduling` -> `closed_won` | 2 |
| `work_done_collect` -> `closed_won` | 2 |
| 4 other one-offs | 4 |

So the LL "Leads" column was showing 40 cards when only ~16 were still leads. **The funnel was lying about the state of the business.**

Fix: the stage is reconciled from the card's **current** `idList`, read on **every** event (not just list moves). That makes it self-healing: a missed webhook delivery, or a move made while a deploy was in flight, is corrected by the next event of any kind on that card.

### Defect 2: the list->stage map must be keyed by ID, never by index

The board's list order and `PIPELINE_STAGES` **do not agree**:

```
Trello  [7] Work Done - Collect Payment      PIPELINE_STAGES[7] needs_follow_up
Trello  [8] Needs follow-Up Service          PIPELINE_STAGES[8] work_done_collect
```

The 2026-08-10 bulk import mapped them positionally, which silently swaps those two columns. `LIST_STAGES` is now keyed by list id, and an unknown list yields `undefined` so the stage is left alone rather than the card being dumped into a wrong column. Pinned in the self-check, since this is invisible on inspection.

**RULE: never map two ordered lists onto each other by index across a system boundary.** The other side can reorder at any time, and it fails silently rather than loudly.

### Defect 3: notes kept the create-time placeholder

Trello writes the card description a beat *after* `createCard` fires, so a card imported inside that window kept `Auto-imported from Trello card "image.jpeg"` forever, losing the real lead text, the contact block, the Contract Name and the HS_ID. `backfillLeadJob` repaired name/leadInfo/labels but never notes. **32 cards affected.** Now repaired, but only when the note still matches that exact placeholder shape, so a note the team wrote is never clobbered.

### Verified on the reported card
After the fix, Miriam Cabrera: `pipelineStage: email_follow_up` (matches Trello), both labels, full `leadInfo`, and the complete lead email in notes including "My solar does not work" and HS_ID 59807628084.

## Authority decision: the app owns the record, Trello is intake only (17b6097)

User: "Apps win Trello for now will be the intake of the lead."

So Trello is where a lead arrives, nothing more. Once the card is on the LL board the office works it in the app, and nothing arriving from Trello may overwrite what the app holds.

| field | rule |
|---|---|
| `pipelineStage` | **NEVER** touched after create. The app owns the column. |
| `labels` | union-**ADD** only, and only while the card is still at `INTAKE_STAGE` ('leads'). Never removes, never reorders. |
| name / `leadInfo` / notes | fill **only where the job's value is empty or still the create-time placeholder**. |

The reasoning for the split: completing an import that Trello delivered incomplete is not an override. `createCard` fires before the description is written and the attachment uploaded (+1s typically, +82min when a human drops the screenshot later), so the follow-up events are finishing the original intake, not making a new decision. A label added seconds after the card is created is part of that same intake, which is why labels union-add during the intake stage but stop contributing the moment the lead is being worked.

This supersedes the stage mirroring added in `9e3a1e6` earlier the same day. That was correct while Trello was the system of record, and the one-time reconciliation it performed still stands (55/55 columns matched Trello at that moment). From here the app is authoritative. `stageForList` survives for the create path alone (which intake list a new lead arrived in), and keeps its by-id-not-by-index self-check assertions.
