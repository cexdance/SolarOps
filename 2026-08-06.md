## Navigate no longer routes every job to Null Island (522ee7d)

**Deployed:** `522ee7d`, live build `v1.7.6.0+522ee7d.1786026397368`, builtAt 2026-08-06T14:26:37Z. Gate: `pnpm build` green, **415/415** tests (was 408).

**Severity was higher than logged.** The open item read as an occasional bug on jobs "with no lat/long". Checking live data first: **all 134 contractor jobs carry `latitude: 0, longitude: 0`**, because nothing geocodes them on write. So `?q=0,0` was every tech, on every work order, routed to a point in the Atlantic ~380 miles off Ghana. 133 of the 134 have a usable address already sitting on the record.

**RULE: measure the blast radius against live data before scoping a fix.** "Some jobs are missing coordinates" and "no job has ever had coordinates" call for the same code but a very different urgency.

**Fix:** `jobMapsUrl()` in `lib/woHelpers.ts`, prefers real coordinates, falls back to the address string. Applied at the single call site that used raw coordinates; every other maps link in the codebase already encoded an address, so the blast radius was one line.

Two decisions:
- **Only the exact `0,0` pair is the never-geocoded sentinel.** A genuine zero on one axis stays valid, so a real equatorial or prime-meridian coordinate is never discarded. Out-of-range values (|lat|>90, |lng|>180) also fall back.
- **Returns `null` when there is neither coordinate nor address** (1 job of 134); the button renders disabled as "No address" instead of linking somewhere wrong. A wrong destination gets acted on, an absent one does not.

**Files:** `lib/woHelpers.ts`, `components/contractor/JobDetail.tsx`, `__tests__/jobMapsUrl.test.ts` (7 tests)

**Verified:** live in-browser on US-15553, the anchor href went from `?q=0,0` to the Gladeview address. Post-deploy, crawled all 23 prod chunks: the old `job.latitude` interpolation is **gone**, the disabled-state copy is present.

**Still open:** `MentionsWidget.tsx:159` renders 3 emoji (staff Ops Center, out of scope for the contractor cleanup). Geocoding itself is still not wired: nothing ever populates lat/long, so the address fallback is now the permanent path rather than a fallback. Worth deciding whether to geocode on write or drop the coordinate fields.

## Customers list looked truncated on mobile (e4bb887)

**Deployed:** `e4bb887`, live build `v1.7.6.0+e4bb887.1786065326589`, builtAt 2026-08-07T01:15:26Z. Gate: `npm run build` green, 431/431 tests (43 files).

**Report:** Cesar, from a phone: "cannot see all the customers, missing a lot on mobile," with a screenshot showing gaps in the customer numbers (US-15666, 15663, 15662 ... 15655, then a jump to 15605).

**Diagnosis: no data was missing.** Two separate things looked like one bug:

1. The customer-number gaps are not gaps. Queried live Supabase: `US-15656`, `US-15654`, `US-15606`, `US-15620`, `US-15640` all return zero rows. Those customer numbers were never created. SolarEdge site ids are not contiguous for this org, so a scrolled list always looks like it is skipping records.
2. The real defect: `Customers.tsx` paginates, and the pager was the last element after 50 table rows. On desktop the page is short enough to notice. On a phone, 50 rows is a very long scroll and the pager was never reached, so the list read as "these are all the customers." 323 customers live, Cesar was seeing 50.

**Fix (2 lines, `solarflow-dashboard/src/components/Customers.tsx`):**
- `PAGE_SIZE` 50 -> 100. 323 customers = 4 pages instead of 7.
- Pagination bar is `sticky bottom-0 z-10`, so it stays pinned to the viewport while scrolling the table. No new state, no scroll listener. Safe because there is no fixed bottom nav in this app (grepped: the `pb-24` on the outer wrapper is breathing room, not a nav offset).

**Deliberately not done:** infinite scroll, or a mobile-only page size. 323 rows in one DOM table will drag on a phone. Revisit only if a continuous list is actually requested.

### Count reconciliation (done after the catalog capture, worth recording)

The catalog screenshot reads "323 of 323 customers," but `app_data` holds 422 `customer:{id}` rows. Reconciled:

| | |
|---|---|
| `customer:{id}` rows in `app_data` | 422 |
| of those, listed in `deleted_customer_ids` | 99 |
| alive | **323** |

323 matches the UI exactly, so the projection is correct and nothing is being dropped. Note for anyone auditing later: **a raw `count(*)` on `customer:%` is not the customer count.** It includes tombstoned records, which stay as rows and are filtered client-side against `deleted_customer_ids` (919 entries, most for ids that no longer have a row). Always subtract the tombstone list before comparing a DB count to a UI count.

### Pattern worth reusing

**"Missing records" is a data claim. Check it against live data before touching UI.** One `count(*)` plus a five-id existence probe against Supabase separated a real UI bug from a non-existent data bug in two queries. Had I trusted the screenshot's framing, the session would have gone hunting for a sync/tombstone clobber that was never there. Same lesson the contractor-geocode item logged: measure blast radius against live data before scoping the fix.

**Rebase before trusting a build gate.** The local `main` was 12 commits behind origin, so the first `npm run build` + `npm test` (403 tests) validated a stale tree. The push rejection is what surfaced it. Re-ran the gate after rebasing and the real number was 431 tests. A green build on a behind-HEAD tree proves nothing about what you are about to ship.

### Follow-ups

- None blocking. The customer-number gaps are expected and need no action.
- Minor, not urgent: 99 tombstoned `customer:{id}` rows still sit in `app_data` and sync to every client as dead weight, and `deleted_customer_ids` has grown to 919 entries. Worth a compaction pass at some point, but it is correctness-neutral today.

## Tombstoned customer rows reaped from the sync payload (b8ee52a)

**Deployed:** `b8ee52a`, live build `v1.7.6.0+b8ee52a.1786066540260`, builtAt 2026-08-07T01:35:40Z. Gate: `npm run build` green, 435/435 tests (43 files).

Follow-up to `e4bb887`, which surfaced 99 dead customer rows as a "minor, not urgent" note. It was not minor: 14% of the customer payload.

### Root cause

`pushToSupabase` builds `dirtyCustomerRows` by filtering deleted customers **out** (`syncEngine.ts`, the `.filter(c => !deletedIds.includes(c.id))`). So a deleted customer's `customer:{id}` row was never updated and never removed. It sat in `app_data` forever, and every client on every pull downloaded records it would immediately discard against the tombstone list. Nothing in the codebase ever issued a DELETE for a `customer:` row.

| | before | after |
|---|---|---|
| `customer:{id}` rows | 422 | 323 |
| orphaned (tombstoned but still stored) | 99 | 0 |
| customer payload | 430,708 B | 368,936 B |

61.7 KB / 14% off every client's pull.

### Fix

Reap in `pushToSupabase`, gated on `isDirty(deleted_customer_ids)`, so a steady-state push costs **zero** extra queries and it only runs when something was actually deleted.

**Ordering is load-bearing.** The reap runs BEFORE the `metaRows` upsert. A failed reap throws, `deleted_customer_ids` never reaches `markClean`, and the next push retries. Reaping *after* `markClean` would mark the tombstone list clean while the rows survived, orphaning them permanently, which is exactly the bug being fixed.

Key batching extracted as `customerRowKeyBatches(ids, size=100)`, pure and exported so it is testable without a live Supabase (the suite deliberately does not test `pushToSupabase`). 4 tests: prefixing, empty list, 919-id chunking with no drops/dupes across boundaries, no trailing empty batch. A single `.in()` with ~900 keys would have been an ~18 KB query string.

### Deliberately NOT done: trimming the tombstone list

`deleted_customer_ids` has 919 entries but only 99 had rows. Trimming the other 820 would let those customers resurrect on the next SolarEdge import or from a stale tab. The whole list is **5.8 KB**. Bad trade, left intact. Rule: the tombstone list is cheap and load-bearing, the dead *rows* were the expensive part.

### One-time prod cleanup

The 99 pre-existing orphans predate the fix, so code alone would not clear them (the reap only fires on the next delete). Applied directly:
1. Backed the 99 rows up to `/Users/cex/solarops-tombstone-reap-backup-2026-08-06.json` (103 KB, **outside the repo**, contains customer PII, do not commit).
2. `DELETE FROM app_data WHERE key LIKE 'customer:%' AND id IN (tombstones)`.
3. Verified: 323 rows, 0 orphans, 919 tombstones intact.

Live customer count is **323 before and after**. The projection was always correct, only the payload shrank. No user-visible change.

### Pattern worth reusing

**A per-record sync entity needs a reaper, not just a tombstone.** The tombstone makes the delete *correct*; without a reaper the delete is never *cheap*. This is a gap in the same family as `sync_job_tombstones`. `deleted_job_ids` (22 entries) has the identical shape and is presumably accumulating the same orphans at a smaller scale, worth the same treatment.

### Follow-ups

- `job:` rows very likely have the same orphan problem (`deleted_job_ids`, 22 entries). Same fix, not applied here because it was out of scope and unmeasured.
- Legacy `customers` blob key still in `app_data` at 48 KB alongside the 323 per-record rows. Unverified whether anything still reads it. Larger single win than this reap if it is dead, but needs a read-path audit first.

## Storage-full modal made diagnosable, job rows reaped (b8dbd07)

**Deployed:** `b8dbd07`, live build `v1.7.6.0+b8dbd07.1786067274299`, builtAt 2026-08-07T01:47:54Z. Gate: `npm run build` green, 441/441 tests (44 files).

Cesar reported the blocking "Storage full, changes not saved" modal is STILL appearing despite ba54944, the 07-22 IDB migration, photoCompress and the photoStore offload.

### The finding that mattered: we could not tell which failure it was

**Two different failures raise the same modal**, and both have always sent a `reason` in the event detail:

| Emitter | reason | Storage | Cap |
|---|---|---|---|
| `dataStore.ts:479` | `idb-write-failed` | IndexedDB | origin quota (large) |
| `contractorStore.ts:541` | `quota-exceeded` | localStorage | ~5 MB per origin on iOS |

`StorageWarningBanner.tsx` read only `detail.kind` and **discarded `reason` and `source`**. So every field report was untraceable without physically holding the device. That is why this kept recurring: each prior fix targeted a plausible cause without evidence of which one fired.

Now recorded via `logChange('storage.warning', ...)` so it lands in the admin Log Viewer, with `localStorage` bytes and `navigator.storage.estimate()`. Those two numbers separate the cases: ~5 MB of localStorage means the per-origin cap; small localStorage with usage near quota means an exhausted origin, i.e. photo blobs in IDB. Cause is shown in the modal footer too.

### The copy was wrong and had to change

Both emitters write to the **cloud first**, before the local write:
- `contractorStore.ts:522` calls `dbSet` before `localStorage.setItem`.
- `dataStore.ts:490` calls `dbSet` with the full state regardless of the IDB result.

So "your most recent edits could not be saved" is false. The edits are in the cloud; what failed is the device keeping its own offline copy. The modal was telling Cesar he was losing data when he was not, which is why it reads as an emergency every time. Retitled "This device is out of storage" with accurate body copy. **Two new tests pin the cloud-write-before-local-write ordering**, because if it ever regresses the modal starts lying.

### Do not trust an agent's conclusion over live data

Fatso's audit (`storage-audit.md`, committed) named `solarflow_contractor_jobs` the top suspect: a whole-company blob, unscoped per contractor, no cap or trim, holding every job's photo arrays for the whole org on every contractor's phone. The **structural** critique is correct and worth fixing.

Its **conclusion** does not survive measurement:

| | |
|---|---|
| blob raw JSON | 300 KB (135 jobs, 4 contractors) |
| busiest contractor's share | 134 KB |
| iOS localStorage cap | ~5 MB |

300 KB cannot fill a 5 MB cap. Scoping it per contractor saves ~55% of a number that was never the problem. Same lesson as the geocode item and the customer-count item, three times in two days now: **measure against live data before accepting a diagnosis**, including one from a subagent.

Evidence points instead at the IndexedDB origin quota (where photo blobs live), which is `idb-write-failed`, not the localStorage path. Unconfirmed, and deliberately not "fixed" blind. The instrumentation is what will confirm it on the next occurrence.

### Upload path: checked, and it is durable

Photos go to IndexedDB **first** (`photoStore.ts:82-101`), then upload to Supabase Storage, with a retry sweep on mount and on regaining connectivity. `saveContractorJobs` strips `data:` base64 before the localStorage write and keeps the `https://` URL once uploaded, so no base64 ever reaches localStorage (now covered by a test). The only unrecoverable window is a narrow one: a photo written to IDB but not yet uploaded, while offline, combined with an origin eviction. Orthogonal to this modal.

### Job row reap (leftover #1 from b8ee52a)

Same bug as customers, confirmed against live data: 11 orphans / 15.5 KB of a 344 KB job payload. Both reaps now share one gated block; `customerRowKeyBatches` generalised to `rowKeyBatches(prefix, ids)`. One-time prod cleanup: 166 -> 155 job rows, 0 orphans, 22 tombstones kept. Rows backed up to `/Users/cex/solarops-job-reap-backup-2026-08-06.json` (off-repo, PII).

### Leftover #2: legacy blobs, audited, NOT deleted

| key | last written | size | items |
|---|---|---|---|
| `customers` | 2026-06-11 | 48 KB | 264 |
| `jobs` | 2026-05-26 | 8.7 KB | 22 |

Both are dead: no reader in `src/` (the only match for the key is a now-stale comment in `syncEngine.ts:17` claiming blobs "are still written as a fallback", which the timestamps disprove), no full-table scan of `app_data` anywhere in `src/`, and `api/` only ever reads specific keys (`CRM_KEY`, and a key passed to `contractor-jobs.ts`). Neither blob is in `KV_SYNC_KEYS`.

**Left in place anyway.** They are 57 KB of dead weight that nothing pulls, so the payload argument for deleting them is roughly zero, while they are the only remaining snapshot of pre-migration state. Deleting them is a one-way door with no upside. Revisit only if `app_data` size becomes a real constraint.

### Follow-ups

- **Confirm the cause on the next occurrence.** The Log Viewer will now carry `reason` + byte counts. That determines whether the fix is IDB photo reclamation or the localStorage path. Do not guess again before that data exists.
- `solarflow_contractor_jobs` scoping: real architectural debt (unscoped, uncapped, whole-company), just not urgent. `mergeContractorJobs` is a verified union by id, so a partial local copy cannot clobber other contractors on push, which makes the fix safe when it is worth doing.
- `solarflow_interactions` (`customerStore.ts:63`) is append-only with no trim. Slow burn, unmeasured.
- Stale comment at `syncEngine.ts:17` should be corrected; it claims blob fallbacks are still written.

## Found it: the change log was eating localStorage (146196b, 5922d79)

**Deployed:** `5922d79`, live build `v1.7.6.0+5922d79.1786068451702`, builtAt 2026-08-07T02:07:31Z. Gate: `npm run build` green, 452/452 tests (45 files).

The instrumentation from `b8dbd07` paid for itself on the first occurrence. Cesar's modal read:

```
quota-exceeded · contractor_jobs · local 5.0 MB
```

### Reading the evidence correctly

That line contains a contradiction, and the contradiction is the whole answer:

1. `quota-exceeded` means the **localStorage cap**, not IndexedDB. Kills the photo-blob/IDB theory.
2. `local 5.0 MB` means localStorage is genuinely at the iOS ceiling.
3. But the throwing write was `contractor_jobs`, and that blob measures **~300 KB**. It cannot be what filled 5 MB.

**The write that throws is not the write that filled the store.** `contractor_jobs` was the messenger. Anyone stopping at fact 3 ships a scoping fix for `contractor_jobs` (as both Fatso and I were about to), saves 165 KB of a 5 MB problem, and the modal keeps firing.

### The culprit, measured not guessed

`changeLog.ts` caps at `MAX_ENTRIES = 2000`, a **count**, which says nothing about bytes. The entries also push to Supabase, so the real per-entry size was measurable from `change_log` without ever touching Cesar's device:

| op_type | entries | avg payload | max payload |
|---|---|---|---|
| `job.update` | 1,898 | **9,685 B** | **1,430,867 B** |
| `job.contractor_update` | 4,432 | 527 B | 1,469 B |
| `photo.delete` | 13 | **115,234 B** | 639,582 B |
| overall avg entry | | **2,040 B** | |

2,040 B x 2000 entries = **3.89 MB**. Plus ~0.39 MB of synced KV keys plus `contractor_jobs` = the reported 5.0 MB, near exactly. And Cesar was **editing a work order**, which is precisely what emits `job.update` at 9.7 KB a time.

### Fix

Full payload still goes to Supabase (the real audit store). The local copy is now disciplined:
- payloads over 1 KB truncated to `{_truncated, bytes, preview}` (size + 200 chars kept for triage)
- serialized log held under 512 KB by dropping oldest, newest always kept
- the byte pass also **reclaims devices already carrying multi-MB logs** from earlier builds, on their first write after this ships

Projected: ~5.0 MB -> ~1.0 MB.

**Recorded caveat:** if the Supabase push fails, `flushPending` retries from the local copy and re-sends the truncated payload. Losing detail on a retried entry beats filling the device, and the entry itself is never lost.

### How the culprit was found without the device

Worth keeping, because "ask the user to paste console output" was avoidable:
1. Summed `app_data`: only **0.39 MB** of cloud data ever lands in localStorage. So a fresh browser login could never reproduce 5 MB, which ruled out driving a browser before wasting a session on it.
2. That proved the bytes were **device-local accumulation**, narrowing it to code.
3. The change log mirrors to Supabase, so `avg(octet_length(...))` on `change_log` gave the exact per-entry size and the projection.

**A local-only store that also syncs is measurable from the server side.** Reach for that before asking anyone to open a console.

### Also shipped (146196b)

`topLocalStorageKeys()` in the modal footer (top 3) and the logged payload (top 8), so a future occurrence **names the occupant** instead of only reporting a total. Key names and sizes only, never values, with a test pinning that.

### Follow-ups

- `photo.delete` averages 115 KB per entry **in Postgres too** (max 639 KB); `job.update` max is 1.43 MB. The local side is capped now, but these payloads are still fat server-side. Worth slimming at the call site.
- `MAX_ENTRIES = 2000` is now redundant with the byte cap; harmless, left alone.
- Still open from before: `solarflow_contractor_jobs` unscoped/uncapped (real debt, ~300 KB, not urgent), `solarflow_interactions` append-only, stale blob-fallback comment at `syncEngine.ts:17`.

## Audit payloads slimmed at the call site (c22f6e6)

**Deployed:** `c22f6e6`, live build `v1.7.6.0+c22f6e6.1786069588780`, builtAt 2026-08-07T02:26:28Z. Gate: `npm run build` green, 458/458 tests (45 files).

Server-side follow-up to `5922d79`, which capped the log on the device but left the payloads themselves fat in Postgres. Measured per-field against live rows rather than guessed.

### job.update: two append-only fields were almost the whole problem

Decomposing `payload->'changed'` across every current-shape row:

| field | changes | avg bytes | total |
|---|---|---|---|
| `auditLog` | 1,185 | 1,983 B | **2.24 MB** |
| `fieldTimes` | 758 | 2,388 B | **1.73 MB** |
| `updatedAt` | 1,159 | 78 B | 0.09 MB |
| everything else combined | | | < 0.10 MB |

3.97 MB of the 4.65 MB that current-shape diffs occupy, more than every other field put together. Both are **append-only**, so each edit grows them and then the diff dumps the full before AND after copies. Logging a job's own `auditLog` inside an audit entry is pure duplication. Both added to `HEAVY_DIFF_FIELDS`.

**Known consequence, accepted:** `fieldTimes` is an object, not an array, so the heavy branch compares truthiness (`b ? 1 : 0`) and its changes now drop out of the diff entirely rather than reporting a count. It is derived merge metadata from the field-level-merge work, not user data, so losing it from the audit trail is fine. Worth remembering if `fieldTimes` ever becomes something a human needs to audit.

### photo.delete: base64 leaking into the audit trail

`url` averaged **114,954 B** (max 639,305 B) for one reason: 3 of 13 rows captured a `data:` base64 URL instead of an uploaded `https://` link, so the entire image went into the audit log. New `describeUrl()` keeps the blob's identity and drops its bytes, rendering `[data:image/jpeg 639305 bytes]`.

This is a general hazard, not a photo.delete quirk: **any audit payload that can receive a URL can receive an entire image.** `describeUrl` is exported for reuse at other call sites.

### The 1.43 MB outlier was not a live bug

Splitting `job.update` by payload shape:

| shape | rows | window | avg | total |
|---|---|---|---|---|
| raw snapshot (legacy) | 395 | 2026-05-16..05-30 | 34,395 B | 12.96 MB |
| diff shape (current) | 1,516 | 2026-06-02..today | 3,219 B | 4.65 MB |

The 1.43 MB row is a **legacy raw snapshot with `woPhotos` at the payload's top level**, written before the diff shape shipped on 06-02. That call site was already fixed months ago. Checking this before "fixing" it saved a change to code that was already correct.

### Pattern worth reusing

**Decompose the payload before slimming it.** Three plausible fixes were on the table (drop `woPhotos`, truncate everything, scope the whole entry) and all three would have been wrong or wasteful. One `jsonb_each` over live rows showed the entire problem was two fields nobody had suspected, and that the scariest number in the table was historical. Same measure-first lesson as the geocode item, the customer count, and the contractor_jobs red herring, four times in two days.

### Follow-ups

- 12.96 MB of legacy raw-snapshot `job.update` rows (May 16-30) still sit in `change_log`. Harmless, and they are audit history, so deleting them is a one-way door with no real upside. Left alone deliberately.
- Still open: `solarflow_contractor_jobs` unscoped/uncapped, `solarflow_interactions` append-only, stale blob-fallback comment at `syncEngine.ts:17`.
