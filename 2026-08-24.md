## c3f8b03 - Contractor Pay: contractor + ALL-time filters

**Live:** v1.7.6.2+c3f8b03.1787541945052, builtAt 2026-08-24T03:25:45Z. `/api/users` returns a JSON 401, so the functions built (not a zero-function deploy).

### What changed and why
Contractor Pay (`contractor-billing` view, rendered by `BillingModule`) already had a DAY/WEEK/MONTH/QTR/YTD/CUSTOM bar but no way to isolate one contractor. Added:

1. **Contractor dropdown.** Options are derived from the `contractorId`s actually present in the job list, not the full roster, so the select never offers a contractor with zero orders. Label resolution is `contactName -> businessName -> email -> id`. `Contractor` has no `name` field, that chain is the real fallback order.
2. **Filter applied in `allJobs`, not `filteredJobs`.** `filteredJobs` only feeds the rendered card list; `allJobs` feeds the `totals` reducer behind the profit / goal / pay-status tiles. Filtering in the wrong one would have shown one contractor's cards under the whole team's money.
3. **ALL timeframe button.** Two reasons: with a contractor selected you usually want their full history, and `getDateRange()`'s `custom` branch returns `customDateRange`, which starts `{start:'', end:''}`, so selecting CUSTOM before typing dates made `jobDate >= '' && jobDate <= ''` false for every row and rendered an empty board. ALL short-circuits before the date comparison.

### Files
- `solarflow-dashboard/src/components/admin/BillingModule.tsx` - `contractorFilter` state, `contractorOptions` derivation, `'all'` added to the `timeframe` union and the button row, the `<select>` above the search box, `Contractor` added to the type import and an optional `contractors` prop.
- `solarflow-dashboard/src/App.tsx:3318` - passes `contractors={contractors}` into `BillingModule` (already in scope at that call site, 5 other components take it).

### Patterns worth reusing
- **In any board with summary tiles, the filter belongs on the array the reducer consumes.** This file has two derived arrays a filter could plausibly go in, and only one of them reaches the money at the top. Check which array the totals read before adding a filter.
- **A date-range filter whose empty state is `''` fails closed on every row.** `'2026-08-01' >= ''` is true but `<= ''` is false, so a blank range renders nothing rather than everything. An explicit ALL that returns before the comparison is cheaper than special-casing empty strings.

### Verified live (localhost, real admin login)
- Timeframe row renders `DAY WEEK MONTH QTR YTD CUSTOM ALL`.
- Dropdown lists 4 real contractors (Carlos Valbuena, Cesar Jurado, Jaime Mendez, Reynaldo Perera) plus "All contractors".
- Selecting Carlos Valbuena narrowed the board 47 -> 13 cards.

### Follow-ups
- Filter selection is not persisted across navigation. Fine for now.
- No multi-select, so two contractors cannot be compared side by side. Add if asked.

### Unrelated thing noticed while verifying
A headless login as an admin lands on **"Restricted - Financial views are available to administrators only"** for `contractor-billing` and stays there for well over 6 seconds after `networkidle`. Only after a ~20s settle does the role resolve and the real screen render. The account is dual-role (admin + IMPower contractor), so the pre-resolution default appears to be the contractor role. Not introduced by this deploy and not chased here, but if a real admin ever reports "Billing says Restricted", this is it: a slow role resolution showing a hard denial screen instead of a loading state. `capture-screens.mjs` only avoids it by accident, it captures 7 other admin screens first, which burns enough time for the role to settle.

## df46e61 - Contractor Pay: client number + contractor on each card

**Live:** v1.7.6.2+df46e61.1787543151271, builtAt 2026-08-24T03:45:51Z. `/api/users` JSON 401, functions built.

### What changed and why
A card showed only customer name + SO id, so two orders for the same customer were indistinguishable at a glance, and seeing who ran a job meant opening it.

- **Client number** (`job.clientId`, US-1XXXX) renders next to the customer name, only when set.
- **Contractor name** joins the location/date meta row with a `User` icon.
- **`contractorName()` extracted** from the `contractorOptions` derivation added earlier today and now shared by the dropdown and the card rows, so the two cannot label the same contractor differently.
- **Client number added to the search predicate.** Displaying an identifier people cannot search for is a trap.

### The one real hazard here
The search line was written `(job.clientId ?? '').toLowerCase().includes(q)`, deliberately NOT `job.clientId?.toLowerCase().includes(q)`. The optional-chained form returns `undefined` on a missing clientId, which is falsy, so every row without a client number would vanish from the board, including on an empty query. That is exactly the Billing search bug from the memory index (`a?.x.includes(q)` IS A FILTER THAT DELETES DATA), one file over. 47 of 47 live job cards happen to carry a clientId today, so the bug would have been invisible until the first row without one.

### Verified live (localhost, real admin login)
- 47 of 47 job cards render a `US-` client number.
- First card reads `Pavel  US-15402` / `SO #cj-1780931049961-n0ml` / `Bay Lake, FL - 2026-08-10 - Jaime Mendez`.

PowerCare service orders now carry a badge on the card, next to the customer name and client number.

### The decision worth recording
The codebase already had **two different PowerCare colorings** before this change:
- `Jobs.tsx:219` - indigo pill, `Zap` icon, label "PowerCare", rendered on the job/lead card.
- `Customers.tsx:108` - orange chip, part of the `CustomerCategory` color map where PowerCare is one category among O&M / New Install / Prospect.

The memory index says "PowerCare = orange", which is the Customers/Dashboard convention, not a global one. Reused the **Jobs badge (indigo + Zap)** because Contractor Pay cards are the same service orders viewed from another screen, and a marker that changes color between two views of the same record is worse than either color on its own. Do not "fix" this to orange without also changing `Jobs.tsx`, they are deliberately the same now.

## 9541e83 - SolarEdge alerts map: customer contact info in popups

**What.** Marker popups on the SolarEdge Alerts map view showed only the client id / site name, the address, the alert count, and the Open / Acknowledge / SolarEdge actions. They now also show the matched customer's name, phone (as a `tel:` link) and email (as a `mailto:` link) below the address.

**Why.** The map is the triage surface for active alerts. Calling the customer meant leaving the map, opening the site panel, then the customer. The contact data was already in memory, just not rendered.

**How.** `SolarEdgeMonitoring.tsx` already builds `customerBySiteId` (`{ bySiteId, byClientId }`) for navigation. Rather than duplicating that index or passing the whole customer array down, the map takes an optional `customerFor: (site) => Customer | undefined` resolver prop. Resolution order matches the rest of the file: `solarEdgeSiteId` first, then `clientId` (guarded, since most `FL_SITES` rows have `clientId: ""` and an empty-string lookup would be a wrong-match risk).

**Files**
- `solarflow-dashboard/src/components/views/SolarEdgeAlertsMapView.tsx` - new optional `customerFor` prop, contact block in the `<Popup>`, `Phone`/`Mail` icons.
- `solarflow-dashboard/src/components/SolarEdgeMonitoring.tsx` - passes the resolver built on the existing memo.

**Pattern worth reusing.** When a child needs a lookup the parent already indexes, pass a *resolver function*, not the raw collection. It keeps the memo as the single source of matching logic and avoids re-indexing per render in the child.

**Verified.** `pnpm build` green, `pnpm test` 594/594 in 65 files. Live: `v1.7.6.2+9541e83.1787574818848` at 12:33:38Z.

**Follow-up not taken.** No copy-to-clipboard button and no "open customer" link inside the popup. The `Open` action already reaches the site panel. Also: sites with no matching customer render nothing extra, no "unlinked" hint. Add if triage keeps hitting unmatched sites.
