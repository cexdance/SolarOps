## a5ccacc  Site transfers land in Ready to Invoice, not Invoiced

**Trigger:** SO-2608-76679 (a site transfer) showed up in the Billing board's Invoiced column immediately after creation.

**Diagnosis: not a data bug.** The live row (`job:job-1787746185962`) is exactly what you would expect for a fresh order: `serviceCode: SITE-TRX`, `serviceType: Site Transfer`, `status: new`, `woStatus: draft`, `invoicedAt: null`, `completedAt: null`, `siteTransferCompletedAt` stamped the same day. It was the RULE, not the record. `getBillingColumn` had a deliberate early branch pinning every site transfer to `invoiced` from creation, on the reasoning that a transfer has no quote and no field work, so Daniel invoices the flat fee directly and the card should not sit in New waiting for stages that never come. Correct premise, wrong destination column: "there is nothing to do before invoicing" means **Ready to Invoice**, not Invoiced. Invoiced is a claim that money was billed, and the board was making that claim on the order's behalf the moment it existed.

**Fix (2 files):**
- `getBillingColumn` (`Billing.tsx:36`): site transfers now default to `to_invoice`. `status === 'paid'` still wins (-> `paid` / `costs_covered`), and a new `status === 'invoiced'` check lets the card advance once it really has been invoiced.
- `moveToColumn` (`Billing.tsx:396`): the drop guard was `col !== 'paid' && col !== 'costs_covered'`, which now also has to allow `'invoiced'`, otherwise the new stage would be unreachable by drag and the card would be stuck in Ready to Invoice forever. Earlier columns stay ignored on purpose: dropping a transfer on Quote Sent writes a stage the board immediately renders back.

**No migration.** The column is derived at render time, so every existing site transfer re-renders into the right place on load. Nothing was written to `app_data`.

**Pattern worth keeping:** *a "skip the pipeline" shortcut has to name the column that means "ready for the next human action", not the furthest column it could plausibly land in.* The comment in the original code was honest about its reasoning and still picked a column that asserts a financial fact. When a board column is a money claim, defaulting into it is the same class of bug as `status: invoiced` with `woStatus: draft`, which the very next lines of that function exist to defend against.

**Files:** `solarflow-dashboard/src/components/Billing.tsx`, `solarflow-dashboard/src/__tests__/billingColumns.test.ts` (site-transfer describe block rewritten, plus a new case pinning the `status: invoiced` -> Invoiced transition).

**Verified:** `pnpm build` clean, `pnpm test` 67 files / 608 tests pass, live `version.json` = `v1.7.6.2+a5ccacc.1787765245637`, `/api/users` returns 401 (functions built, not a Vercel NOT_FOUND).
