### What changed and why

**1. "Storage full, changes not saved" root cause.** It was never localStorage. `photoStore.ts` had no eviction path at all: every work order photo stayed on the device at full size forever, including long after `mirrorRow` stamped a `supabaseUrl`. IndexedDB quota is per ORIGIN, not per database, so a fat `solarops_photos` starved `solarops_state` and made every `idbSetState` write fail, raising the blocking modal.

Fix: `purgeUploadedBlobs()` drops the blob from rows that are uploaded, have a `supabaseUrl`, and are older than 30 days. The row and its metadata stay, so `hydrateWoPhotos` still resolves the photo by falling back to `supabaseUrl`. Recent rows keep their bytes so field crews with no signal still see current jobs. A row with an unparseable `createdAt` is kept, never reclaimed. Runs once per boot, fire-and-forget, never blocks startup.

**2. Dead `solarops_report_<id>` localStorage writes removed.** Nothing in the app or the API ever read the key back, and an older shipped build stored whole report HTML in it, so it accumulated until the origin quota blew. `App.tsx` sweeps orphans already sitting on existing devices.

**3. Trello import passthrough (same deploy).** Customer create now passes through `activityHistory`, `files`, and `trelloBackupUrl` instead of dropping them via the field whitelist.

### Patterns worth reusing

- **IDB quota is per origin, not per database.** One greedy store starves every other store on the same origin.
- **A mirrored cache must eventually drop the original.** Write the eviction path in the same change as the append path, not later.
- **Grep for the READER first.** `solarops_report_<id>` had a writer and zero readers, and it was silently eating quota.
- **A red local build does not mean the committed tree is broken.** The TS2550 seen here was uncommitted WIP. `git stash push -- <one path>` gates the committed tree without disturbing a dirty tree.
- **Re-check `git status` for files that went dirty mid-session.** A stray `imapflow` dependency nearly shipped.

## Broken WO photo links: repaired (bedcb42)

`scripts/photo-link-repair.mjs`, run against prod.

**Cause.** Two historical upload paths wrote the same contractor photo under two storage keys: `wo-photos/<jobId>/<photoId>.jpg` and `<jobId>/<category>/<photoId>.jpeg`. Byte sizes confirm exact twins. A later cleanup deleted the redundant object without rewriting any record, and `dedupeWoPhotos()` keeps the FIRST-seen twin by URL stem with no idea whether that twin still resolves. So a job could keep the dead URL and drop the live one.

**Result.** 2 photos restored by repointing at the surviving twin (verified HTTP 200 with real bytes). 23 entries that could not render on any device were dropped: 7 on WO-2604-54207, 4 on WO-2606-20049, 12 on job-1784646838098. Their stems went into `job.deletedPhotoStems` so the App.tsx contractor reconcile pass cannot re-import them. Only stems with no live object are ever ledgered, so a repaired photo is never blocked. Re-run of the script now reports 0 dead across all 34 jobs with photos.

**Rules**

- A dedupe that picks a winner by name must not assume the winner still exists. `dedupeWoPhotos` collapses `.jpg` and `.jpeg` twins to one stem and keeps whichever came first in the array.
- Deleting a storage object is only half a delete. Every record pointing at it has to be rewritten in the same pass, or the pointer outlives the file.
- The 15 entries with no storageUrl, no dataUrl and no photoStoreId are residue of the 2026-08-04 blob:-URL incident: `stripEphemeralPhotoUrls` correctly drops a dead `blob:` dataUrl and keeps the entry for `photoStoreId` recovery, but when there is no photoStoreId that leaves an entry pointing at nothing.

## P0 OPEN: photo uploads have been failing since 2026-07-21

**Not a single object has landed in the `customer-files` bucket since 2026-07-21.** `change_log` has 16 `photo.upload_fail` rows on 2026-08-03 (jobs `job-1785352459232`, `job-1784646838098`, both admin and iPhone sessions), every one `new row violates row-level security policy`.

**Not a session problem.** The same client writes `app_data` and inserts `change_log` rows at the same timestamps, and both policies require `auth.role() = 'authenticated'`. The session is genuinely authenticated.

**Reproduced in SQL under `set local role authenticated`:**

| statement | result |
|---|---|
| `INSERT` a brand-new object key | allowed |
| `SELECT` from `storage.objects` | 0 rows, the row is invisible |
| plain `UPDATE` of an existing object | affects 0 rows, silently |
| `INSERT ... ON CONFLICT DO UPDATE` on an existing key | `42501 new row violates row-level security policy` |

**Mechanism.** `storage.objects` has policies for INSERT, UPDATE and DELETE but **no SELECT policy**, so an existing object row is invisible to `authenticated`. `uploadPhotoToStorage` passes `{ upsert: true }`, which is `INSERT ... ON CONFLICT DO UPDATE`: it cannot take the update branch on an invisible row, and Postgres reports it as an RLS violation. Uploads therefore fail whenever the target key already exists. The content-addressed key change (`contentHashId`, same bytes always map to the same key) makes that collision the normal case rather than a rare one.

**Proposed fix (NOT applied, pending review):** add the missing SELECT policy.

```sql
create policy "Authenticated users can read"
  on storage.objects for select to authenticated
  using (bucket_id = 'customer-files');
```

The bucket is already public for reads, so this grants no access that a public URL does not already give. Verify afterwards by re-uploading a photo that is already in the bucket.

## The "2 pre-existing TS errors" were not code errors

Chased the long-standing pending item for `api/notify.ts` and `api/ups-tracking.ts`. There is nothing to fix.

The repo root has its own `package.json` declaring `@types/node`, `@vercel/node`, and `@types/web-push`, but root `node_modules` was never installed. Any `tsc` run over the root `api/` tree in that state reports:

- `TS2307: Cannot find module '@vercel/node'` / `'web-push'`
- `TS2580: Cannot find name 'process'`

That is the environment, not the code. After `npm install` at the repo root:

```
./solarflow-dashboard/node_modules/.bin/tsc --noEmit --strict --types node api/notify.ts api/ups-tracking.ts
```

returns clean, under both bundler and node module resolution. `npm run build` in `solarflow-dashboard` is also green (warnings only: a PostCSS `@import` ordering warning, static/dynamic import overlap on `supabase.ts`/`syncEngine.ts`/`db.ts`/`dataStore.ts`, and a >500 kB chunk notice). No files changed.

**Rules learned**

- Before "fixing" a TypeScript error in a tree that has no `node_modules`, install first. Missing-module and missing-global errors are environment noise.
- Root `api/` is covered by NO tsconfig. Applying the dashboard's app lint flags to it (`noPropertyAccessFromIndexSignature`, `noImplicitReturns`) invents dozens of TS4111/TS7030 errors that were never in force there. Do not chase them.
- A pending item copied forward across sessions can be stale. Reproduce it before budgeting work for it.
